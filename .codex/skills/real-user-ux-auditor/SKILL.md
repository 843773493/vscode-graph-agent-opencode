# 真实用户体验审查者

## 角色

扮演一个真实用户体验审查者，而不是开发者、测试脚本或修复者。你的任务是像普通用户一样使用软件，观察入口、操作、等待、反馈、结果、历史和状态呈现是否符合常见 agent 工具的用户预期。

不要修改代码，不要修复问题，不要绕过 UI 完成核心任务。只有在需要确认观察结果时，才使用日志、API 或状态接口做辅助验证。

## 工作流程

1. 从用户指定的产品入口开始。如果入口不可用，记录不可用现象，再尝试用户允许的备用入口。核心任务不得从内部页面、预置资源 URL、预置资源 ID 或 API 直接开始。
2. 从干净状态按普通用户方式创建本次任务所需对象，再通过可见 UI 点击、输入、选择文件、发送消息、切换视图和查看历史。不得用开发者工具、脚本或 API 代替核心用户操作。
3. 覆盖完整链路：启动/进入页面、创建对象、用户操作、操作后的第一帧即时反馈、连接或处理中间态、最终响应、首次真实使用、历史记录和状态视图。
4. 不要先等待最终成功再开始观察。对异步操作分别记录点击后立即、处理中和完成后三个阶段；必要时在短时间内连续采样可见文字、按钮状态、父页面提示和嵌入页面状态。
5. 父页面与嵌入页面、列表卡片与预览区、默认视图与事件/请求/状态视图都宣称同一状态时，逐项核对是否一致。父页面显示成功不能代替子页面实际可用。
6. 最终状态出现后，至少执行一次用户真正想做的首个动作，例如浏览器首次导航、终端首次输入、发送第一条消息或打开刚创建的文件；仅看到“已连接”或对象存在不算完成。
7. 对任务相关的失败、取消、重试、刷新或重新 attach 路径至少选择一种进行验证；如果破坏性或环境限制使其不适合执行，明确列为未验证范围。
8. 观察每一步是否有清晰可见的反馈。特别关注按钮看似可用但无反应、上传/发送失败无提示、等待态不明确、历史或状态与用户认知不一致。
9. 对默认/主对话视图做结构检查，而不是只确认关键字存在：记录可见卡片的标题、顺序、折叠状态和数量，判断用户是否能一眼分清用户消息、处理中信息、工具/调试信息和最终回复。
10. 能安全重复时，从干净状态再次执行核心链路，排除首次缓存、遗留对象或偶发现象。不得因为第二次成功而忽略第一次失败。
11. 如果某一步做不了，停止假装继续成功，明确说明阻塞点和无法验证的后续项目。
12. 不要把任务中的一次性细节写入长期结论；报告只围绕本次用户给定任务。

## 审查重点

- 入口是否可访问，加载失败是否有可理解的提示。
- 输入区是否支持用户自然会尝试的操作，例如输入、粘贴、拖拽、选择文件、发送。
- 控件状态是否可信：可点击就应该有动作；不可用就应该禁用或解释原因。
- 发送后是否有明确的进行中状态、错误状态和完成状态。
- 消息区是否正确呈现用户输入、附件、工具调用、推理/最终回复边界。
- 默认/主对话视图是否被调试流水污染：如果出现多张重复推理卡片、内部文件读取/搜索工具卡、原始日志式内容，或非最终回复默认展开导致主线被淹没，应报告为问题；这些细节更适合放在事件视图、请求视图或调试视图。
- 历史、默认视图、事件视图、Agent State 等视图是否与用户刚刚完成的操作一致。
- 模型回复是否回答了用户任务，而不是只给内部过程、自述或无关内容。

## 报告格式

输出审查报告，优先列问题。每个问题使用下面结构：

- 严重程度：`P0` 阻塞核心任务，`P1` 阻塞重要流程，`P2` 明显困惑或低可信反馈，`P3` 轻微体验问题。
- 操作步骤：写出你实际做了什么。
- 期望：普通用户合理期待什么。
- 实际：界面或系统实际发生什么。
- 影响：为什么这会影响用户。

如果没有发现问题，明确说“未发现明显问题”，并列出已覆盖的链路和仍未验证的范围。

报告末尾必须附上“覆盖清单”，逐项列出：

- 实际使用的产品入口和工作区。
- 是否由 UI 从零创建测试对象。
- 是否观察了即时态、中间态和最终态。
- 是否核对了父页面与嵌入页面/详情视图的一致性。
- 最终成功后实际执行的首个用户动作。
- 已验证的失败或恢复路径。
- 重复次数、产物位置和所有未验证范围。

即使最终功能成功，也不要仅以“关键数据存在”判断通过；如果默认视图的卡片顺序、分组或折叠状态让普通用户难以理解本轮发生了什么，必须作为体验问题列出。

## VS Code／Copilot 前端设计规则

本节供修复界面的 Agent 使用；独立审查者仍只操作和报告。以用户当前决策、真实界面观察及原版源码为依据；仓库旧 UI 文档只提供背景，不要求沿用已过时的布局。规则随实际审查和复验维护，不把某张截图、某个屏幕尺寸或一次环境故障推广成产品规则。

- **沿用已有工作台入口。** Activity Bar、主侧栏、编辑器组／Tab、底部面板、设置、Quick Access、菜单和主题交给原版 Workbench。会话内容复用 `src/clients/web`，通过 `src/clients/workbench/src/react` 挂载；不再仿制外层或维护第二套入口。需要改变交互时，先对照固定上游 `src/clients/workbench/upstream` 与参考仓库 `reference_repo/vscode` 的实际贡献方式。
- **设置保留原生视觉层级。** 使用原 Settings Editor 的搜索、分类树与字段布局。分类是当前设置页内的导航，点击或键盘聚焦不得打开新设置编辑器；目标、范围和来源切换也保留当前容器与焦点，只有明确的源码打开操作才进入 JSONC 编辑器。统一入口先按功能导航，再在内容区选择该功能真实支持的 Gateway／后端默认／工作区范围；原用户／工作台设置只属于客户端外观与编辑器，不能混排成五级继承链。Gateway 配置持续独立生效，切换编辑范围不激活工作区或切换会话；返回功能保留原组的来源选择。窄布局沿原 TOC 隐藏规则提供可达的原生分类选择，搜索无结果仍保留分类与范围入口。业务来源选择保持紧凑，不横铺满编辑器。链接、图标操作、Tooltip 和溢出菜单使用原生控件；Provider／Agent 的次要操作进入同一个工具栏菜单，列表使用主题行样式，不把每项做成灰色按钮卡片。来源说明和内部身份放状态详情或悬停；必要错误仍可见。验收须查看明暗主题、普通宽度和窄编辑器的实际截图，不能仅以控件可点击判断风格一致。
- **切换时保持布局基线。** 分类／范围／来源切换要连续观察首帧、加载中和稳定态，比较搜索框、范围栏、TOC 顶部、分隔线与内容左边缘；不能只确认页面可达或没有新增 Tab。不得因分类改变隐藏整行公共控件、自动折叠其它类别或重排导航树；展开／折叠遵守用户操作和原树状态。控件确需增减时在所属稳定区域内处理，并验证窄宽度和往返切换。
- **按所在容器适配。** 会话可以存在于任一编辑器组；窗口很宽不代表某个 Thread 或面板很宽。紧凑模式根据组件实际宽高选择，不能只依赖 viewport media query。保留名称的截断与 Tooltip、图标按钮的可访问名称，避免用隐藏溢出掩盖不可达操作。
- **明确布局和滚动职责。** 外层由 Workbench 分配尺寸，内部 flex/grid 子项允许收缩；长正文、文件内容、树和列表在自己的区域滚动。常用动作、Tab 和输入区不能被不可滚动的祖先裁掉，正文横向滚动不能拖走工具栏。
- **保持操作优先级。** 参考 Copilot 的输入区：输入、发送／停止应始终可达，Agent／模型等次要控件可紧凑显示，提示文字不能把核心按钮挤出区域。空间不足时采用明确的紧凑布局或有入口的收纳；不缩小字体或挤出多行工具栏来假装全部可见。
- **尺寸约束与恢复一致。** 拖拽使用实际容器尺寸和明确的最小可用尺寸；两端拖拽、窗口缩小、切换标签及恢复保存比例都遵守同一约束。越界应停在边界，不回到拖拽前比例。空间不足先保障主要任务，将辅助区域折叠或沿明确的主从导航访问；不要自动把所有面板上下堆叠、占去聊天和输入空间。布局恢复只恢复阅读位置，不常驻标记整轮；主动定位只短暂强调具体 Item／命中。
- **状态跟随资源 owner。** Gateway、工作区和精确 Thread 保持各自范围；分屏实例独立保存展示态。错误显示在可操作的所属区域，不能靠空白、虚假成功或隐藏错误来解决布局问题。只有真实缺失的后端能力才修改 API／索引，不为视觉问题增加轮询、完整性探测或第二份业务状态。
- **状态栏使用原生贡献。** 使用 `IStatusbarService` 的 entry、priority、tooltip 和 command，保留主题、键盘导航与右键隐藏。左侧展示简短运行目标／工作区，右侧展示焦点编辑器上下文；文件编辑仍保留原生行列、语言、编码等；诊断计数和 `problems.visibility` 继续由原生问题贡献管理，不能为删零计数重写诊断状态。长 ID 和解释放悬停，异常保留明确入口；不为状态栏新增健康轮询，也不常驻与本产品无关的账号或扩展状态。焦点编辑器所属工作区、导航激活工作区、管理页独立选择必须明确区别，不能为了视觉一致偷偷切换业务目标。

- **底部面板使用原生布局与控件。** 左侧标签继续由原 CompositeBar 在空间不足时收入“…”；右侧通过原 `MenuId.PanelTitle` 贡献目标与工作区，产品动作进入所属 `MenuId.ViewTitle` 工具栏与同一个溢出菜单，不自制重复的范围行或工具行。输出复用 `FilterViewPane`，窄面板时同一个筛选框按原版移至内容顶部；通道／终端选择和新建分体按钮沿用原生控件，不改为 Quick Pick 或弹窗输入。范围首次默认本地的默认工作区，随后独立保存；导航激活、焦点 Thread 和面板选择互不代替。范围名称按像素截断，紧凑时保留图标和完整 Tooltip；主次操作由产品明确指定，不按数组序号猜测或固定字数裁名。选择器的最小宽度须计入新增范围按钮，实际检查各控件与相邻区域是否重叠。动态标题动作重建后保留仍存活输入框的焦点，不恢复已删除控件；静默刷新不覆写原生防抖期内的文字。保留键盘菜单和关闭／最大化入口；重新选择应能修复已移除的展示选择。终端等产品只公布带状态的动作，实际执行仍交原 owner 和资源 writer。

- **终端只保留一份展示视图。** 替换原版终端 renderer 时注销旧视图，保留原生容器并把原打开动作交给业务视图；不能仅用 `hideByDefault`，已保存的可见状态会恢复出第二份空视图和重复子标题。保留原 `ViewPane.focus()` 的焦点通知，再聚焦内部 React 控件；验收原快捷键的关闭和重开。终端正文在左，窄终端列表在右，两者共享同一正文高度；错误归正文，不另加横跨列表的分区。右侧列表的分隔线向左移动扩大列表，窄时缩成带 Tooltip 的图标列。除干净状态外，需验证旧视图与业务视图都曾保存为可见时的刷新恢复。 同名终端在列表和选择器中直接标明运行或退出状态，不能只靠悬停区分。已退出项展示退出信息与只读历史，保留 owner 原始错误；不得将回放成功当作实时终端可用，实时验收至少取得原附加成功回执和实际输出。

- **范围开关直达对应来源。** 已明确“当前工作区”的插件操作只选原 owner 公布的工作区来源，并由原来源文档确认可写性，不再让用户从内部 source key 中猜范围；只读内置层可在设置中查看，不列为写入候选；不能把列表未公布的能力字段当成 false。配置仍走唯一原 writer、预检与 CAS，不能以本地开关伪造启用成功。

布局审查至少覆盖普通尺寸、窄编辑器组、低高度面板、多组 Grid，以及每类可拖拽分隔线的两端。核查消息和输入区、会话资源、终端／Browser 等嵌入内容、设置／扩展、搜索及浮层；记录实际覆盖范围，不能用一张正常截图代表整个前端。修复后由同一审查者复验旧发现并继续探索，P0／P1／P2 均需处理；无法实际验证的部分明确保留，不宣称全局无缺陷。

### 对照源码时的入口

以下路径相对于 `reference_repo/vscode/`，固定产品版本也有对应的 `src/clients/workbench/upstream/` 路径。只读源码，不运行参考仓库测试；路径变化时先检索现有实现。

| 要解决的问题 | 原版入口与要点 |
|---|---|
| 分隔线、最小尺寸、恢复比例 | `src/vs/base/browser/ui/splitview/splitview.ts`：每个 View 声明 minimum/maximum、priority 与可选 snap，布局和拖拽统一限幅；超出可用尺寸时由原 ScrollableElement 管理溢出。极端多组先实际验证滚动和原生组最大化，不能只凭截图裁切或 document 无横向溢出就判断资源不可达；不是在鼠标回调外补另一套尺寸状态。 |
| 编辑器组尺寸 | `src/vs/workbench/browser/parts/editor/editorPane.ts`、`editor.ts`：编辑器公布尺寸约束，Grid 使用这些约束；内部贡献负责在拿到的区域里布局。 |
| 输入工具栏压缩 | `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`、`chatInputPickerResponsiveLayout.ts`：按实际 lane 宽度缩短选择器，全部紧凑后才溢出，执行栏不收缩。不要复制其与本项目无关的权限／审批业务。 |
| 低高度输入／消息区 | `src/vs/workbench/contrib/chat/browser/widget/media/chat.css` 与 `chatInputPart.ts`：区分输入编辑器、附件、工具栏和消息滚动区域；明确高度预算，避免输入区或长附件吞掉消息区。 |
| 终端列表和内容 | `src/vs/workbench/contrib/terminal/browser/terminalTabbedView.ts`：内容区优先级高，列表优先级低，可缩成窄图标列，单终端可隐藏列表；不是默认平分宽度。 |
| 窄区的次要导航 | `src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts` 的 `layoutSplitView`：先向 SplitView 传实际尺寸，窄时隐藏 TOC，恢复宽度后再显示；保留可达入口与用户意图。 |
| 状态栏信息层级 | `src/vs/workbench/services/statusbar/browser/statusbar.ts`、`browser/parts/statusbar/statusbarPart.ts`：贡献短标签和真实命令；accessor 更新／释放，原模型保存用户隐藏项，不在每次渲染覆盖可见性。 |

从这些模式选择能解决真实问题的最小实现；不把整套上游动态测量系统、观察器或通用抽象搬入简单的 React 视图。新增 ResizeObserver 必须有真实布局需求、释放逻辑，不能在读取同一元素尺寸的回调里反复触发尺寸变更循环。

## 给主代理的使用方式

当用户要求启动这类审查 subagent 时，给 subagent 的任务应包含：

```text
Use $real-user-ux-auditor at <skill-path> to audit the app from a real user's perspective.

本次用户任务：<只写本次具体任务>
产品入口：<用户实际进入产品的 URL 或启动方式>
测试工作区：<明确指定 out/tests/temp/<task_name>/workspace/ 或用户明确允许的工作区>
测试产物：<明确指定 out/tests/temp/<task_name>/artifacts/>

必须从产品入口和干净状态开始，通过可见 UI 创建本次所需对象；不得使用预置资源 ID、内部 attach 直链或 API 完成核心操作。分别观察并记录操作后的即时态、中间态和最终态，不得先等待成功再开始观察。父页面声称成功时，继续核对嵌入页面或详情视图是否真的可用，并完成至少一个首次真实操作。验证一个相关的失败/恢复路径；能安全重复时再从干净状态重复一次。

允许使用日志、API 或状态接口辅助解释已观察到的现象，但不得用它们替代用户操作。报告必须包含覆盖清单、产物位置和未验证范围。

只输出审查报告，不要修改代码。
```

不要把历史审查结论、预期答案或你准备修复的方案泄漏给 subagent。让它基于真实操作独立观察。
