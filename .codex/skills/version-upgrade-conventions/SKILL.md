# 版本升级与迁移约定

在提出目录树、命名或实现迁移前，先确认业务域、实际数据来源、来源版本、目标结构及原 owner，再选择落点；不能从文件名猜测支持范围。

## 准则来源

- 阅读根 [AGENTS.md](../../../AGENTS.md) 的“已验收版本与迁移边界”。
- 阅读 [worktree 与发布迁移约定](../../../docs/architecture/worktree-and-release-policy.md) 的“release 支持基线”“开发中间态与迁移”“迁移目录与边界”。
- 阅读受影响 owner 的 `AGENTS.md`、版本清单及实际读写入口；用户当前裁定优先于本技能。下面的目录示例不构成扩大支持范围或修改环境的授权。

## 来源与支持范围

- 默认根据最近两次经用户完整验收并用于发布的固定提交 `R_current`、`R_previous` 识别旧契约；准备下一版以 `R_current` 为来源并明确候选 SHA。普通提交、目录名和 Agent 测试通过不能代替发布证据。
- 根/dev/实验的未验收中间数据不自动成为兼容合同。用户明确要求额外来源时，登记该来源及支持边界，核实旧源码和数据语义；不能仅凭文件名推测格式。
- 缺少发布基线时报告缺口并继续独立功能，不新增猜测兼容，也不据此删除已有迁移。未知版本或数据取舍保留原件并交用户决定；已支持且无需取舍的来源自动升级，不重复索要确认。

## 目录、命名与版本

**迁移源码按域和版本组织；日期只用于实验、证据与备份，不决定执行顺序。**

### 格式转换的统一命名

新增格式转换文件统一使用：

```text
v<来源版本>_<来源格式>_to_v<目标版本>_<目标格式>.<实现语言后缀>
```

业务域由 owner 目录体现，文件名直接体现两端版本和格式。使用小写格式名和下划线；Python 用 `.py`，实际 SQL 脚本用 `.sql`，不因目标格式而决定实现语言。格式名称按实际存储选择，例如 `jsonl`、`json`、`sqlite`、`csv`、`protobuf`，不限于这几个名称。已知具体数据库时使用 `sqlite` 等实际名称，避免笼统的 `sql`。

```text
<业务域 owner>/<该域迁移目录>/
├── v1_jsonl_to_v2_sqlite.py
├── v2_sqlite_to_v3_jsonl.py
├── v3_jsonl_to_v4_jsonl.py      同格式的结构／语义升级也适用
└── v4_jsonl_to_v5_protobuf.py
```

上述版本和格式仅为示例，不要求实际项目经历这些步骤，也不固定转换方向。后一发布版换回原格式是新的正向迁移，不能因此复用旧版本号；它与显式回退不是一回事。对应的聚焦测试沿用迁移文件名并加 `test_` 前缀。

- 这里的版本是本业务域明确登记的数据格式／结构合同版本；软件发布版与它的关系通过现有版本声明和发布证据核实，不把软件 SemVer、数据版本和 SQLite schema 版本混为一个编号，也不新增映射账本。
- 若旧格式没有版本号，先核实来源并明确其版本归属，再命名；不能为套模板擅自认定为 `v1`。多段版本标识写入 Python 模块名时将点替换为下划线，例如实际 `1.2` 表示为 `v1_2`。
- 文件名用于查找，不用于自动发现或决定执行顺序。执行链由原 owner 清单显式登记，不扫描文件名排序；不要只命名为 `legacy_import.py`、`recovery.py` 或 `v1_to_v2.py`，遗漏格式和目标信息。

### 归属与已有迁移

- 转换代码归原业务数据 owner，不论来源和目标是什么格式。配置域转换归 `configs/migrations/<domain>/`，跨资源协调归既有维护入口；不能因为使用 Python 或目标是数据库就改变业务归属。
- 复用 owner 已有的迁移目录；其目录约束不适合格式转换时，在该 owner 内按职责选择落点并同步约束，不强行塞入只允许 SQL 的目录，不为示例预造目录。转换后正常业务只使用已发布的目标格式，不固定要求 SQLite，也不保留源格式双读／双写。
- SQL 结构和迁移语句放 SQL，执行协调留 Python。已有 `001.sql` 等有序 SQL 名称不因新增格式转换规则而重命名；沿原版本清单执行，不重排已登记步骤。新建库和新格式初始化仍归原 owner，不复制一套 schema 或写入实现。
- 数据格式变化沿本域合同登记目标版本；只有实际数据库结构变化才提升数据库 schema 版本。抽离 SQL、搬文件或向现有结构导入数据，不单独构成提升 schema 版本的理由。
- 已发布迁移原则上冻结；清理历史步骤前核对支持基线、初始化和升级依赖。两个发布基线不意味着版本只能相邻，不能截断必要链路。

## 唯一升级与恢复链路

- 识别支持来源后，沿既有生命周期只读预检、停止原 writer、取得原 owner 锁、备份、迁移及校验，成功才恢复服务。预检能确定的未知来源和取舍冲突应在停旧及首次写入前暴露。
- 普通配置 loader、业务请求及热更新不偷偷执行离线结构迁移；自动入口和显式维护入口复用原 owner，迁齐调用方后移除旧读写链，不保留双读、双写或第二事实源。
- 复用各存储 owner 的既有事务与发布原语。涉及 SQLite 时复用 `SQLiteStateDatabase`，锁内核版本，备份包含已提交 WAL，有序链与校验在提交前完成，失败回滚且不开放写入。旧进程仍存活时不能升级它正在使用的旧结构。
- 当前版本重复启动不重复备份、重写或全库校验。中断恢复沿既有 journal 的冻结计划幂等继续；显式回退不得在下次启动被自动反转。没有跨资源恢复需求时不新增 journal、账本或通用调度框架。
- 普通 I/O 和运行故障明确失败并保留原件，不当成用户取舍，不伪报成功；不扫描磁盘猜修复，不清理来源未确认的数据。

## 实现与验收

先列出本次明确来源、目标版本、owner 和有序步骤，再纵向迁齐写入方、直接／间接消费者及测试。仅整理命名时不扩成数据迁移或批量重命名历史文件。

按改动风险验证真实入口、原件备份、身份／顺序／归属、事务失败、中断重入和重复启动；涉及回退时验证恢复方向。完整执行历史验收通过产品入口生成关键状态，不能用手工填库替产品完成待验证步骤。所有测试沿仓库现有隔离、超时及内存保护，记录来源 SHA、候选、命令、退出码和未验证范围；平台验收按本次要求执行，局部通过不能替代。

交付前复审有无更简单的单链路实现，删除本次多余适配层、fallback、重复状态和兼容分支。未实现或用户延期的关键项保留 TODO，不勾选为已完成。使用本技能不自动授权同步 dev/release/main、发布或修改真实用户数据。
