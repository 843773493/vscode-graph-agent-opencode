# 配置文件约定

在处理配置前先加载本技能，并查看项目已有的配置加载顺序、合并语义、schema 校验方式和相邻命名。优先保持现有行为兼容；只有新增配置时才应用下面的规范，不要为了统一命名而无计划地重命名历史文件。

## 文件命名

默认配置统一使用 JSONC，文件名遵循：

```text
{base}.jsonc
{base}_{ex}_{ex}_{ex}.jsonc
```

其中 `{base}` 使用稳定的名词，通常来自项目名、进程名或 `setting` 等配置主体名称；`{ex}` 是从宽到窄排列的场景后缀，说明配置变体或应用范围。新增文件优先使用小写、下划线分隔，并保持同一配置族的 base 不变。

推荐的配置族：

```text
setting.jsonc             # 默认配置，作为基线
setting_schema.jsonc      # 默认配置的 schema 或约束描述
setting_dev.jsonc         # 源码开发场景的覆盖配置
setting_dev_local.jsonc   # 本地开发覆盖，仅供当前机器使用
```

约定如下：

- `{base}.jsonc` 是默认入口；不要把默认配置命名成 `default_{base}.jsonc` 或另造平行的默认文件。
- `_schema` 表示 schema/约束，不是运行时覆盖配置；schema 应与默认配置及最终合并结构保持一致。
- `_dev`、`_test`、`_prod` 等后缀表达运行场景；先写场景，再写更窄的范围，例如 `setting_dev_local.jsonc`。
- `_local` 表示个人或机器私有覆盖。仓库中的 `_local` 配置不得被 Git 跟踪；新增这类文件前检查 `.gitignore`，必要时加入精确规则（常见写法为 `*_local.jsonc`），并用 `git check-ignore -v <file>` 验证。不要擅自删除已经被跟踪的历史文件，应报告并按迁移任务处理。
- 尽量不要为一次性差异创建新的后缀文件。能用现有覆盖层表达的差异就放入现有变体；确有新的稳定场景时，使用能说明用途的名词后缀。
- 新代码默认读取 `{base}.jsonc`，其他文件只有在明确选择场景或本地覆盖时才加载。若加载器支持分层，推荐顺序为默认基线 → 场景覆盖 → 本地覆盖，但必须以项目实际合并语义为准。
- `.jsonc` 是本约定的默认格式。若外部协议、工具或历史兼容要求固定使用其他格式，不要强行改格式；应在变更说明中记录例外。

## 参数结构与命名

新增参数必须先按功能分组，再预留可扩展的第二层命名空间，第三层才放实际生效参数。这个约束只适用于新增参数，不要求为了统一层级改造当前已有参数；已有参数优先保持 schema、加载器和外部行为兼容：

```jsonc
{
  "runtime": {
    "shell": {
      "timeout_ms": 30000,
      "output_limit_bytes": 1048576,
      "retry_count": 2
    }
  }
}
```

按以下规则设计：

- 第一层是用户能理解的功能域，例如 `runtime`、`providers`、`permissions`、`storage`、`logging`；不要把孤立参数直接铺在根层。
- 第二层是稳定且可继续扩展的子系统、协议或应用对象，例如 `runtime.shell`、`providers.models`。同一功能未来应能在这里增加兄弟参数或兄弟对象，而不是再次修改根层结构。
- 第三层是实际生效参数，例如 `timeout_ms`、`output_limit_bytes`、`retry_count`。新增参数至少要能明确回答“属于哪个功能域、哪个扩展点、具体控制什么”。
- 同一类参数保持“名词在前、扩展在后”：`timeout_ms`、`retry_count`、`output_limit_bytes` 优于 `ms_timeout`、`count_retry`、`bytes_output_limit`。单位、格式、范围等限定放在核心名词后。
- 当未来会出现多个同类对象时，使用 map/list 或对象集合保留扩展空间，例如 `providers.models.<name>`；不要把对象名编码进一串不断增长的字段名，如 `provider_openai_enabled`、`provider_anthropic_enabled`。
- 名称要描述用户可观察的语义，不要把实现细节、临时 issue 编号或当前唯一实现写进公共配置名。布尔值只用于真正的开关；存在多个模式时优先使用有文档约束的枚举或对象结构。
- 参数应有明确默认值、合并行为、取值边界和是否可被本地覆盖的说明。若某字段只适合开发或测试，放入对应变体，不要污染默认配置。

## 旧参数短期兼容

扩展结构时，短期兼容旧参数，但内部只保留一份规范化结果：

1. 新参数成为文档、schema 和新配置示例中的首选；读取时同时识别旧参数。
2. 解析优先级固定为“新参数显式值 → 旧参数显式值 → 默认值”，并在代码和测试中明确冲突时的结果。
3. 新旧字段统一转换到同一个内部模型，不要让业务代码到处判断两套名称，也不要把同一个值复制维护在两处。
4. 标记旧参数为 deprecated，说明迁移方式、保留期限或移除条件；必要时给出一次可定位的警告，但不要在普通启动中反复刷屏。
5. schema、加载器和测试覆盖兼容窗口：至少验证仅新参数、仅旧参数、两者同时存在以及都缺省四种情况。兼容期结束后再单独提交删除旧参数的变更。

## 配置版本与迁移

为配置族维护配置级版本，不为每个参数单独维护版本。配置版本与软件发布版本相互独立：软件版本表示程序发布物，配置版本表示可持久化配置的结构和语义契约；不能因为软件发布版本变化就机械升级配置版本，也不能用软件版本替代配置迁移版本。当前项目的 Gateway 和 Workspace 是两个独立配置域，各自维护自己的 `config_version`；同一配置域的默认、开发和本地变体共享该配置域版本，不能把两个配置域或软件版本强行绑定成一个版本号：

```jsonc
{
  "config_version": 3,
  "runtime": {
    "shell": {
      "timeout_ms": 30000
    }
  }
}
```

按以下策略控制版本和兼容窗口：

- 可以按发布周期建立版本窗口，在窗口内合并多个兼容性改动；新增可选字段、增加默认行为且不破坏旧文件时不必升版。
- 对尚未版本化的既有配置族，可以明确建立初始版本 `v1`；缺少版本字段的旧文档按 `v1` 解释。建立这个基线本身不是迁移，不要因此虚构旧参数或迁移脚本。
- 不要为了遵守时间窗口而延迟不兼容版本升级。发生字段重命名、层级重组、取值语义改变或字段删除时，应在发布新行为前递增配置版本。
- `_dev`、`_test`、`_local` 等同一配置族的变体通常共享配置版本；只有能独立加载、独立发布的配置文档才单独版本化。
- 运行时兼容当前版本和上一个版本即可作为默认支持窗口。更旧版本应由显式迁移命令处理，或给出清楚的升级路径；不得让用户在无提示的情况下启动后得到部分生效的配置。
- 读取版本后，先把旧结构规范化到当前内存模型，再执行当前 schema 校验和业务启动。不要先用当前 schema 拒绝旧结构，导致迁移逻辑无法运行。
- 已知的旧参数可以在内存中临时兼容并给出一次警告；结构复杂、存在信息丢失或改变安全语义的迁移，应要求用户显式运行迁移命令，不要静默猜测。
- 旧参数被明确废弃时，提示配置文件、旧路径、新路径或替代方案、当前版本和迁移命令。未知字段不能一律静默丢弃；至少在诊断模式或严格模式中报告。

维护一个显式的迁移工具或迁移模块，仅在需要改写用户文件、跨多个版本升级、合并/拆分字段或删除旧结构时使用。迁移实现应满足：

- 迁移步骤可重复执行，并以 `vN -> vN+1` 的小步链组织；
- 支持预览/检查模式、备份或可恢复写入、原子替换和失败报告；
- 最新运行时可以只保留当前版本与上一版本的临时加载兼容，但离线迁移工具要么保留可跨版本执行的历史链，要么明确拒绝超出支持窗口的旧版本并给出中间升级方案；
- 迁移完成后写入新版本并重新运行 schema 校验；
- 测试仅旧参数、仅新参数、新旧冲突、缺少版本号、跨多个版本、重复迁移和迁移失败等情况；
- JSONC 重写时保留注释和可读格式，或在命令输出中明确告知格式变化。

## 当前项目的配置合并

当前项目有两个互不混合的配置域：`gateway` 和 `workspace`。每个配置域使用同一配置族：

```text
gateway_inline.jsonc      # Gateway 发行包内置默认配置
gateway.jsonc             # Gateway 用户级覆盖
gateway_schema.jsonc      # Gateway 最终结构 schema
gateway_dev.jsonc         # Gateway 源码开发完整配置模板
gateway_local.jsonc       # Gateway 用户级机器私有覆盖，不纳入 Git
workspace_inline.jsonc    # Workspace 发行包内置默认配置
workspace.jsonc           # Workspace 用户级覆盖
workspace_schema.jsonc    # Workspace 最终结构 schema
workspace_dev.jsonc       # Workspace 源码开发完整配置模板
workspace_local.jsonc     # Workspace 用户级机器私有覆盖，不纳入 Git
```

合并规则必须按加载边界解释，而不是把所有 JSONC 文件自动叠加：

1. `gateway_inline.jsonc` 与 `workspace_inline.jsonc` 是发行包随代码分发的完整内置默认配置；`.env` 仍由环境/安装流程单独管理。`*_dev.jsonc` 是完整开发模板，不是运行时自动参与合并的覆盖片段。
2. Gateway 的有效配置按“`gateway_inline.jsonc` → 用户级 `gateway.jsonc` → 用户级 `gateway_local.jsonc`”生成，并读取 `gateway_schema.jsonc` 校验；不读取工作区 `.boxteam/` 中的 Workspace 配置。
3. Workspace 的有效配置按“`workspace_inline.jsonc` → 用户级 `workspace.jsonc` → 用户级 `workspace_local.jsonc` → 工作区 `${workspace}/.boxteam/workspace.jsonc`”生成；高优先级配置覆盖同名值。对象递归合并，标量直接覆盖，数组整体替换，不能对数组隐式去重或拼接。
4. schema 校验对象是合并后的最终 Workspace 配置，不是工作区覆盖片段单独的完整配置。覆盖片段可以只声明需要覆盖的字段，但不得包含 Gateway 字段。
5. `_local` 文件是可选的用户级机器私有覆盖；当前项目的 `gateway_local.jsonc` 和 `workspace_local.jsonc` 会被显式加载，分别位于对应用户级配置目录。它们必须被 Git 忽略，且来源必须出现在配置诊断接口中。
6. 所有合并失败、schema 错误、未知字段和版本不匹配都必须直接报告，不得返回部分合并结果或静默忽略。

## 变更工作流

处理新增或修改配置时按此顺序检查：

1. 先记录 Git 状态和已有改动，找到配置族的 `{base}.jsonc`、schema、各场景覆盖文件和实际加载入口，确认文件命名与加载优先级，不凭文件名猜语义。
2. 将一次变更限制在一个配置族和一个明确的加载边界内，优先实施最小的端到端垂直切片；不要顺手重命名其他配置族或重写全局配置架构。
3. 判断变更属于默认配置、稳定场景变体还是私有本地覆盖；选择最窄且可复用的文件，不把 `_local` 内容写入默认或提交到仓库。
4. 为新参数选择第一层功能域和第二层扩展点，再命名第三层实际参数；检查同类参数是否保持名词在前、扩展在后，并考虑下一项同类需求如何添加。
5. 判断变更是否改变配置契约；需要时递增配置版本，并同步更新 schema、默认值、配置示例、加载/合并逻辑和迁移工具。
6. 若旧名称仍在兼容期，添加新旧参数的优先级、启动警告、迁移命令与迁移测试。没有真实迁移命令或写回路径时，不要伪造已完成的迁移能力，只实现并报告边界内的临时内存兼容。
7. 除非直接支撑配置行为，否则不要修改技能文件、`AGENTS.md`、安装说明或无关模块；不要用全 workspace 构建替代受影响 crate 的 focused test。
8. 检查 Git 状态和忽略效果：确认不新增被跟踪的 `*_local.jsonc`，并确认变更没有把秘密、机器路径或个人凭据写入受跟踪文件。
9. 运行项目提供的 schema 校验、配置单元测试和受影响的 focused tests；报告实际加载的配置层级、版本兼容行为、迁移结果和未验证的边界。

执行节奏与停止条件：

- 先选一个具体的旧输入、新输入或配置字段，完成“解析/兼容转换 → 当前结构校验 → 一个 focused test”的最小垂直切片，再决定是否扩展到更多字段或场景。
- 读完加载入口后不要继续无界分析；若无法在当前边界内确定安全的迁移语义，停止改动并报告阻塞点、已检查路径和建议的下一步。
- 不要为了证明技能可用而创建虚假的版本号、迁移命令或配置文件；所有用户可见的提示都必须对应真实实现。
- focused test 不可用或耗时异常时，记录原因并返回已有证据；不要用全 workspace 构建掩盖尚未完成的实现。

交付前快速自检：

- 是否存在且唯一的 `{base}.jsonc` 默认基线？
- 新文件是否符合 `{base}_{ex}...jsonc`，后缀顺序是否从宽到窄？
- schema 是否描述最终合并结构，而不只是某一个覆盖片段？
- 新参数是否具备“功能域 → 扩展点 → 生效参数”三层语义？
- 是否考虑了下一项同类参数、用户覆盖方式和默认行为？
- 配置版本是否反映结构/语义契约，而不是机械跟随时间或单个参数？
- 运行时兼容窗口和离线迁移工具的职责是否分离？
- `_local` 文件是否被 Git 忽略且未被跟踪？
- 旧参数是否按明确优先级短期兼容，并有迁移出口？
