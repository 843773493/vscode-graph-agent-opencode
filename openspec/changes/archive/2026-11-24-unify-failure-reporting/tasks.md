## 2. 贯通已有公共错误出口

- [x] 2.1 将现有公共消息提取与诊断记录职责理清：未知异常默认保留脱敏后的原 message、类型和已知阶段；Python／Node SDK 分别提供本语言唯一必要原语，产品异常映射留在原产品出口。不新增 formatter 注册表、异常基类要求、装饰器或二次报告服务。
- [x] 2.2 接通 Pydantic／已有 JSON schema 校验的通用字段路径和原因提取，排除 input／context，保留字段段和未知 code。公开载荷及原报告出口的有界 traceback／stack／cause 统一脱敏，不采集 locals，不再传 raw exc_info／Error；诊断正文默认≤64 KiB、堆栈帧合计≤64，原因后代／深度复用 8／4，原更严格限制优先。在选定节点和帧内复用标准格式化原语，累计预算后停止，不先完整渲染再裁剪，不用轮转代替构造预算。凭据仅用当次已持有值，不读取完整密钥库／环境，不借异常属性或 ContextVar 保存，不建秘密注册表或报告线程／沙箱。
- [x] 2.3 实现原更严格预算优先的公共常量：项目构造／持久化的公共 Error 和消费侧公开提取载荷 JSON UTF-8≤16 KiB，message≤8 KiB，issues≤32 项，cause／errors 总后代≤8、深度≤4；有界遍历并累计预算，先处理秘密再裁剪，保留主原因／原关联／截断标记，不先复制整个异常或上游 data。HTTP／MCP／DAP 原载荷不套用该公开错误预算。沿原协议字段生成并迁齐所有消费者，删除重复格式化，不新建双写字段或替换标准信封。此项数据预算不代表默认 UI 视觉长度，展示收敛另验 6.3、6.5–6.9。
- [x] 2.4 补充少量定向契约检查：未登记异常、空消息、校验问题、超长 stderr、深层／大量 cause／ExceptionGroup 及原错误加报告失败。分别验证公开错误与诊断正文的字节／帧／节点预算，以及构造阶段不遍历／格式化全部原因（不能只断言最终字符串长度）；用同一凭据验证 API、事件和原日志堆栈／cause 都安全且主原因仍可读。不穷举异常类型或新增高频 UI 测试。

## 3. HTTP 与 Gateway 透明传输

- [x] 3.1 复用 TraceMiddleware／原异常 handler 和 API 状态映射，让本层产生的失败保留原因、层次及真实 request_id，客户端沿现有 HTTP 解析读取；不叠加第二个中间件，不修改既有 4xx／5xx／权限／冲突语义。
- [x] 3.2 核对本地／远端 Gateway 和插件代理，已收到的下游错误保持原协议与请求关联；不为 16 KiB 公开错误预算新增正文缓冲、解析、脱敏或重编码，秘密由原 owner 构造出口处理，公开提取在原消费 adapter 完成且不写回原对象。连接尚未建立、响应头超时、原传输超限及响应开始后故障分别沿原 transport 处理，不能改写第二个 HTTP 响应或重放调用。

## 4. 聊天失败终态与历史恢复

- [x] 4.1 扩展原 converge_execution／checkpoint facade，将 failure 固定保存于原 TERMINAL_CONVERGENCE 提交的 storage_commits.metadata_json，与 execution／Turn 状态及 history revision 同事务提交。历史沿原 view／revision 和 terminal execution 关联读取，不扫 commits 猜原因。覆盖首个 Item 前失败和无 Turn 的内部执行，不增建 failure 表、可变 error_message 或协调器。
- [x] 4.2 原失败收尾先提交 rollout，再从已提交结果派生 message stream failure／snapshot；在已有 reconcile_stale_executions 的 Job 决策前读取精确 admission／execution 已提交终态，不将已结束执行恢复为活动 Job、不重放工具或追加固定 execution_lost Trace，沿原 owner 收尾队列／claim。reconcile_unfinished_streams 复用同一终态读取端口，按原结果及稳定事件身份补齐，保留 resumed job 跳过规则。普通查询只读；同一commit镜像冲突报错，合法后续cancelled／interrupted修正沿原writer路径交付，不复用旧event_id覆写、不改变first-end游标或重复完成通知。贯通summary/detail及消费者。
- [x] 4.3 贯通 ConversationView、缓存／合并／memo 和 Turn 展示；移除基于 failed 固定显示“后端没有提供可用的失败详情”的逻辑。metadata 不计 Item、不创建消息，摘要即可取得原因，旧记录缺失时仅表述未记录。
- [x] 4.4 通过真实发送入口制造工具配置校验失败，验收 Item=0、实时终态、断连回放／snapshot、刷新历史及详情展开原因一致；测试错误归属与旧响应不能串到其它 Thread，不手工填 Trace 或 metadata 代替入口。
- [x] 4.5 在原持久化入口注入 rollout 提交前／提交后但 Job 收尾或 stream 闭合前的进程中断，经真实启动恢复入口分别验收成功、失败和取消／中断：Job 不恢复执行、不重放工具，Trace 不追加相矛盾 execution_lost，消息流／历史保持原结果；无已提交终态才沿原恢复／丢失判定。核对队列／claim 收尾、重复恢复零新增终态／零重复执行，以及失败落盘自身失败不能宣称提交成功；不以只调用消息流 helper 代替完整恢复入口。
- [x] 4.6 通过原执行入口覆盖模型 A 失败回退 B 成功、工具 isError 后继续成功，以及失败后显式恢复为新 execution：attempt 保留错误，成功 Turn 无 failure；旧快照保留旧失败，新活动／成功不继承它。不改回退或恢复策略。
- [x] 4.7 覆盖原owner允许的execution_lost→cancelled／interrupted后续提交，以及同一commit镜像内容冲突；合法修正正确显示并保留旧快照、first-end游标、幂等与首次完成通知语义，真正冲突明确失败。复用已有控制修正装具，不新增历史扫描或状态机。
