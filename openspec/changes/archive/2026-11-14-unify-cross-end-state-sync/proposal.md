## Why

当前跨端同步分别由请求代际、活动事件、目录事件、局部回执和定期镜像协调，同一业务状态的接收、应用、展示与清理缺少共同规则，容易重复刷新、迟到覆盖或在断连后无法确认提交结果。需要提供可复用的默认同步机制，同时让小对象、分层目录与大型历史选择适合自己的传输方式，减少业务代码中的重复协调。

## What Changes

- 统一资源归属、同步版本、数据覆盖范围与缓存新鲜度的协议语义，区分资源版本、事件游标、命令身份和网络请求身份。
- 提供小对象完整读取、集合分页与失效重读、历史快照与游标续读三种明确模式；先实现本次切片需要的能力，不为未接入领域预写实现。
- 统一需要可靠提交的命令回执、重复提交识别、结果未知时的查询和前端本地操作记录交接；同步命令直接返回应用结果，不强制变成异步任务。
- 写入回执返回对应资源的提交版本，确认读取携带最低版本，旧镜像只能预览；Goal 同客户端串行提交，多客户端按控制版本进行原子冲突检查，冲突不自动覆盖。
- 消息发出前按操作身份冻结不可变正文和可恢复附件输入，恢复不依赖可变 Composer 草稿；Goal 只同步有界展示对象，内部逐 Job 记账明细不随普通响应或事件传输。
- 首批纵向迁齐 Goal／会话执行状态、用户消息提交与 FIFO 队列、会话目录及 Gateway 镜像；每条链路迁齐协议、生产者、消费者后删除旧协调逻辑。
- 明确前端队列交接给后端队列、后端开始执行及业务终态的区别，复用dispatch队列水位拒绝迟到快照，空队列仍保留已确认水位；终结拒绝的输入可编辑／丢弃后清理，结果未知保留对账依据，同步清理不删除业务数据或改变 Goal 保留行为。
- 快照与事件恢复之外，复用既有调度轻量确认当前可见资源的权威版本，覆盖业务提交成功但通知未产生的情况；不新增全局通知outbox或全量审计。
- **BREAKING** 调整首批接口和事件的同步元数据及命令确认合同，全量迁移调用方，不保留旧协议双读、双写或兼容适配层。
- 保持浏览器经当前 Gateway 路由；中转 Gateway 不新增每请求持久化账本。目录镜像可独立同步，不成为所有业务响应的落盘屏障。

## Capabilities

### New Capabilities

- `cross-end-state-sync`: 跨端读取、命令确认、事件恢复及清理的共同规则与最小实现；包含 Goal 和会话执行状态的首批接入要求。

### Modified Capabilities

- `session-fifo-message-delivery`: 补齐客户端提交与服务端 FIFO 的身份交接、结果未知对账、队列与 Job 状态同步；保留既有 FIFO、投递边界及出队后不保证崩溃重试的业务契约。
- `scalable-session-navigation`: 增加目录页版本验证、Gateway 镜像新鲜度、前端范围缓存和变更失效的统一同步要求，保留分页、搜索语义及现有过期游标错误。

## Impact

- 协议：`proto/` 为公开跨进程类型唯一源，沿现有生成链更新 Python／TypeScript 产物与 DTO；不再建立一套手写公共协议类型。
- 前端：`src/clients/web` 的 Goal controller、会话状态、消息提交／pending 队列、目录 outbox 与资源树；纯同步逻辑放入现有客户端共享核心，DOM 展示留在 Web。
- 后端：Goal owner、Job／pending queue owner、会话导航 owner；持久化与事务仍归原 owner，不新增全仓命令库或统一业务数据库。
- Gateway：业务透明代理、现有 workspace observation 和目录镜像 owner；多目标状态按稳定归属隔离，不要求跨工作区全局一致快照。
- 与 `refine-workbench-layered-caches` 分工：沿用其缓存归属、释放和 stale 边界，本变更负责业务同步；与 `add-workbench-quick-access` 共用目录分页、搜索和错误合同，不重复开发搜索 Provider。
- 当前主 `scalable-session-navigation` 规格仍有物理树权威等历史描述，与用户当前 SQLite catalog 约定冲突；本次仅新增同步要求，实施前核对对应导航变更的规格归并，不据旧描述重建扫描链路。
- 已获用户授权按 Goal、消息 FIFO、目录镜像三个纵向切片并行实施。项目尚无已验收发布基线，不为开发中间数据添加自动迁移或历史兼容；后续迁移仅按用户明确需求单独确定。
