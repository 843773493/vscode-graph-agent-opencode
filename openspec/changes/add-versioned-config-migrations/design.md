## Context

当前配置由用户文件、可选 overlay 和工作区文件合并，内置工具与自定义工具均使用 `module:function` 字符串。源码删除函数后，配置仍能通过结构校验，直到 Agent 构建才失败；工作区覆盖还可能让只修用户配置的操作无效。配置热重载已有候选快照与原子提交边界，可以承载迁移后的验证。

## Goals / Non-Goals

**Goals:**

- 每个持久化配置文件独立、幂等、原子地升级到当前版本。
- 内置工具配置与 Python 文件结构解耦，并在配置加载阶段完成解析验证。
- 普通启动自动升级，CLI 提供显式 migrate 和只读 doctor。
- 保留历史会话和错误事件，旧会话重试使用当前有效配置。

**Non-Goals:**

- 不删除或改写历史会话错误事件。
- 不让 Gateway 直接解析或修改远程/本地工作区业务配置。
- 不长期保留已删除 Python 工厂的兼容函数。
- 不在本次变更中迁移任意第三方插件格式。

## Decisions

### 每个来源文件先迁移再合并

`ConfigService` 使用迁移器分别读取用户文件和工作区文件；迁移成功并写回后才执行 merge。相比只迁移最终有效对象，这能避免旧 overlay 在后续启动再次覆盖新值，并能准确报告来源文件。

### 版本放在根级 `config_version`

整数版本从 1 开始，缺失版本视为 1。迁移注册表以 `from_version -> callable` 串联，任何缺失步骤直接失败。相比依据字段猜测版本，显式版本可审计且测试边界明确。

### 内置工具使用 `tool_id`，自定义工具保留 factory

配置项采用互斥联合：`{"tool_id": "read_context"}` 或 `{"name": ..., "factory": ...}`。内置注册表属于 Agent 工具装配层，注册表解析后仍生成现有 custom tool spec，减少业务层改动。相比给旧函数加 alias，此方案不会形成永久兼容层。

### 原子写回且不生成长期备份文件

迁移先在内存中校验完整候选，再用同目录临时文件、fsync 和 `os.replace` 写回。失败保持原文件不变；迁移日志记录版本和文件路径。自动产生大量备份会污染用户目录，因此回滚依赖原子失败保证，显式 CLI 可在未来增加可选备份参数。

### 热重载迁移失败保持最后有效快照并显式变红

沿用现有 snapshot store：候选迁移或预检失败时不提交，但日志、reload status 和 API 必须暴露详细错误。它不是静默降级；运行时明确处于 unhealthy 状态。

## Risks / Trade-offs

- [迁移自动写用户文件可能令人意外] → 仅执行确定性版本步骤，日志记录 before/after version，doctor 可预览。
- [自定义 factory 导入可能有副作用] → 预检只解析模块属性和可调用性，不实例化工具。
- [多进程同时迁移同一文件] → 原子替换避免半写；写回前比较读取内容与当前磁盘内容，变化时失败并要求重试。
- [旧配置没有版本] → 明确定义为版本 1，并以 fixture 覆盖所有已发布旧形态。

## Migration Plan

1. 引入当前版本、迁移器、稳定内置工具注册表和 schema 联合类型。
2. 更新默认配置生成器为当前格式。
3. 在 ConfigService 启动与 watcher 重载路径接入逐文件迁移和工具预检。
4. 扩展 `python -m configs.boxteam` 的 migrate/doctor 子命令。
5. 用旧 fixture 验证迁移，再运行真实独立后端热重载和旧会话重试 E2E。

回滚代码时，当前版本配置仍只含稳定 `tool_id`，旧代码无法读取，因此发布前必须确保新运行时和迁移同时交付；不提供自动降级写回旧 factory。
