## Purpose

规定本地交互请求和普通用户操作的软件内部总延迟上限，以真实客户端、Gateway 与工作区后端的完整结果为验收依据，避免逐层完整性检查、重复初始化和独立超时累积导致普通操作默认等待十几或几十秒。

## ADDED Requirements

### Requirement: 普通交互必须遵守完整链路延迟预算

系统 SHALL 在服务就绪、本机回环、无外部依赖等待时满足：不超过512KiB的普通业务 API 暖读 p95≤500ms、单次≤1500ms；工作区列表／当前工作区／目录三步导航总 p95≤1000ms、单次≤2000ms；正确会话 Composer 可操作与原版文件正文可见的每次打开≤2000ms；首次未缓存业务数据读取≤3000ms。已有更严格的历史 reader 预算 MUST 保留。

计时 SHALL 包括排队、所有内部请求、初始化、鉴权、完整性校验、序列化及重试，直到完整响应或真实可用界面；MUST NOT 仅计最后一个 helper、先返回 loading、给每层重置完整预算或减掉内部校验耗时。外网／模型／用户等待与构建／进程启动须单列，不冒充普通 API 的软件成本。

#### Scenario: 多层快速步骤累计超过总预算
- **WHEN** 导航三个请求分别完成但总耗时超过2000ms，或一次普通暖读耗时1600ms
- **THEN** 性能验收失败并保留原样本和 request_id，不因每个阶段未超过自己的进程 timeout 就判通过

### Requirement: 暖读不得重复执行无变化资源的全量审计

普通读取 SHALL 保留鉴权、归属、CAS、版本和实际使用数据的必要校验；全库完整性审计、全历史扫描／hash 重算及全体资源预检 MUST NOT 无条件进入每次暖读。可复用的验证事实 SHALL 由原 owner 持有并按数据／schema版本失效；异常与实际变化仍须明确校验或拒绝，不能吞错、关闭校验或以旧缓存冒充新成功。

#### Scenario: 无变化会话重复打开
- **WHEN** 同一会话在版本未变时被重复 bootstrap 或读取小页历史
- **THEN** 返回同一精确 owner 的当前结果，满足完整延迟预算；迁移／恢复的全量检查不随每次普通读取重复执行

### Requirement: 验收必须使用真实入口和未筛选样本

验收 SHALL 包含真实 Workbench／Gateway／Backend 的目录导航、会话打开和后端 URI 文件编辑器打开，核内容、owner、request_id、响应字节与 DOM 规模；无响应替身或预写浏览器缓存。暖 API 至少20次记录原始时长及 nearest-rank p50/p95/max，首次读取单列；单次硬上限不得被平均值掩盖，不能自动重试、删除慢样本或只报告最快结果。

#### Scenario: 快响应返回错误对象
- **WHEN** 请求耗时达标但响应为空、归属错误、request_id 不一致或目标正文未显示
- **THEN** 功能与性能联合验收失败，不能以空成功或占位 UI 获得性能通过

### Requirement: 性能失败必须保留归因证据且禁止扩大默认验收

测试 SHALL 使用进程外超时／内存保护并保留准确命令、源码指纹、原始输出、失败阶段和实际退出码；进程期限不代替交互预算。新增完整性检查或性能断言的注释 SHALL 说明触发边界与计时终点。性能失败须先定位本次链路，不自动全仓重跑、放宽业务断言、改环境或增加生产监控。

#### Scenario: 一次超预算后诊断
- **WHEN** 真实浏览器操作超过预算
- **THEN** 保留这次原始样本、请求身份、页面及必要截图，报告具体范围；没有相关变化不重复运行以碰运气取绿
