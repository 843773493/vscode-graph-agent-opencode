## Context

当前 LiteLLM 在包导入时同步调用 HTTPX 下载目录，默认五秒是网络阶段超时，不是应用初始化总期限。项目的 Chat、Responses、Embedding 和能力注册均可能触发首次导入；主线程只在特定测试中开启官方本地开关。

## Goals / Non-Goals

提供一个运行时导入入口、可复用成功缓存和有界后台刷新。不修改安装包、不加载 LiteLLM Proxy、不新增数据库或改变 Provider 请求配置；本切片不增加公共 JSONC 参数，运行时策略通过明确构造参数设置，默认前台一秒、后台三十秒。

## Decisions

- 在 `app/runtime/litellm_runtime.py` 内串行完成首次导入，仅在导入期间使用官方本地开关并恢复原环境。所有生产直接/间接 SDK 导入迁到该入口；保留懒加载，纯消息转换模块不提前导入 SDK。
- 进程内单个后台线程运行官方异步 refetch、校验和有限重试，另加整体期限，使用独立 HTTPX client，避免被业务模型回放 transport 捕获。线程有界且为 daemon，不能阻塞进程退出；完成回执先保存缓存并暂存结果，下一次请求准备时采用，后台不修改在途模型状态。
- 用户级 `cache/model-metadata/<来源hash>.json` 只保存公共目录、来源和获取时间，先写同目录临时文件再原子替换。缓存新鲜期一天，刷新失败五分钟后允许重试；同一时刻只有一个刷新。损坏缓存与网络失败明确警告，按用户授权继续使用旧表。
- 采用新目录沿用上游 Proxy 的目录更新合同：替换目录、失效大小写查询索引、更新已知 Provider 模型集合、重新应用官方 runtime registrations。此处只调用 SDK 能力，不引入第二套注册事实。
- SDK、ChatLiteLLM 和 HTTP handler 的懒导入统一由运行时模块暴露。原模型流控制仍负责回放 transport，Provider 请求准备先消费已完成刷新，再安装可选回放；Embedding 也走同一入口。

## Risks / Trade-offs

- 上游仍需环境开关控制导入 → 串行导入、立即恢复、覆盖原环境保留测试；上游有稳定导入选项后移除这段暂时控制。
- 旧目录可能不识别新模型 → 保留显式 model_info 与 runtime registrations，记录刷新失败，不把业务请求失败改写为元数据成功。
- 进程可能在后台刷新中退出 → 当前旧表继续有效，原子缓存只发布完整结果，下次进程可重新尝试。
- 正在运行的 SDK 全局查询并非历史快照 → 只在后续请求准备采用完整目录，不修改已有模型对象或封存 assembly，不承诺 SDK 内部全部计价查询固定于单一版本。

## Migration Plan

同一切片迁齐全部生产 SDK 导入及请求准备调用方，再运行受保护单元测试、真实本地 HTTP/冷进程验证和 Provider 同步/异步回放回归。无 schema 版本或业务数据迁移。
