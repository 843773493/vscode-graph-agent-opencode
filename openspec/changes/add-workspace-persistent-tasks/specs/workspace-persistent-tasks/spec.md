## Purpose

定义统一归属工作区的持久任务行为，使用户能够组合定时或事件触发、脚本或模型条件判断、上下文发布与会话执行，并在暂停、重启和重复通知后保持可追踪的一致进度。

## ADDED Requirements

### Requirement: 持久任务必须归属唯一工作区

每项持久任务 MUST 绑定唯一稳定工作区身份，其定义、调度进度、判断及运行记录 MUST 存放在所属工作区 `.boxteam/` 内。Gateway MUST 仅定位工作区、管理后端生命周期及代理请求，不得持有任务定义或执行任务调度。新建任务未指定工作区时 SHALL 使用既有启动配置解析出的 home 下默认工作区；任务保存后不得因界面切换而改绑。

#### Scenario: 未指定工作区的新任务
- **WHEN** 用户从无显式工作区参数的入口创建持久任务
- **THEN** 系统使用启动配置的默认工作区并返回其明确身份，该任务与普通工作区任务遵守同一管理及恢复规则

#### Scenario: 显式工作区与多工作区后端
- **WHEN** 同一后端已挂载工作区 A、B，用户在 A 创建任务后切换到 B
- **THEN** 任务仍归属 A，B 的查询和调度不能读写 A 的任务进度，独立后端也不得顺带创建未指定工作区

### Requirement: 任务组件必须支持统一组合与校验

系统 SHALL 支持由触发器、判断器、判断及动作上下文构造器、执行动作和运行策略构成的持久任务。触发 MUST 支持定时、关联工作执行结束、外部通知及手动触发；判断 MUST 支持规则、脚本与独立判断 thread。组件类型、版本及配置 MUST 在保存时验证；模板和自定义组合 MUST 使用同一任务定义，不得隐式换用未知组件。

#### Scenario: 从模板调整成自定义组合
- **WHEN** 用户创建脚本条件模板并修改触发周期、条件和投递提示
- **THEN** 保存结果是一项完整任务定义，模板视图与高级组件视图读取同一配置及 revision

#### Scenario: 不支持的组件版本
- **WHEN** 用户提交工作区不支持的判断器类型或版本
- **THEN** 系统拒绝保存并返回具体组件错误，不创建看似可运行的任务

#### Scenario: 规则匹配冻结输入
- **WHEN** 规则通过有效JSON Pointer读取本次冻结输入并与expected比较
- **THEN** 系统按JSON值语义返回wait或proceed及明确结果，不启动脚本或额外判断模型；缺失字段与JSON null、bool与number必须区分，对象键顺序不影响相等且数组顺序必须保留

#### Scenario: 纯规则检查中断
- **WHEN** 后端在规则检查阶段退出后恢复，且原任务revision仍有效
- **THEN** 系统从原冻结输入重算纯规则并沿原运行继续，不读取当前外部状态代替原输入，也不将它记作未知脚本副作用

### Requirement: 定时执行必须是统一条件任务的无附加条件组合

所有持久任务 SHALL 遵循“触发 → 判断 → 动作”：触发器决定何时进行一次判断，判断器决定本次是否执行。普通定时任务 SHALL 表达为定时触发、显式的无附加条件判断与动作，不建立独立任务模型或专用执行链路。时间到期 MUST 由调度器计算，不得为判断时钟启动脚本或模型；始终通过判断不产生额外脚本或模型执行。添加附加条件 MUST 修改同一任务定义，不改变其身份或已有计划进度。

#### Scenario: 每天九点执行
- **WHEN** 普通定时任务配置每天九点执行且没有附加条件
- **THEN** 每个有效计划点产生可追踪触发，无附加条件判断通过后执行动作，未到期不启动判断脚本或模型，也不因首次满足策略使任务只执行一次

#### Scenario: 给定时执行开启脚本条件
- **WHEN** 用户对既有定时任务开启脚本附加条件
- **THEN** 原任务身份和时间计划保留，到期后使用脚本决定是否执行，仍走同一触发、判断与动作链路

#### Scenario: 缺失或非法判断配置
- **WHEN** 提交的任务没有有效判断组件配置且不符合模板显式生成的无附加条件配置
- **THEN** 系统明确拒绝，不能将缺失或未知判断器静默解释为通过

### Requirement: 脚本检查必须区分等待与失败

脚本判断 SHALL 在明确的执行位置以配置的运行期限执行，输出结构化判断和可供提示构造使用的结果。未满足条件 MUST 表示正常等待；启动失败、超时及无效输出 MUST 表示可观察错误，不得当作条件不满足。外部脚本 SHALL 也能通过带幂等键的工作区入口提交通知，无需创建 Goal。

#### Scenario: 服务从未上线到上线
- **WHEN** 定时脚本前两次返回服务未就绪，第三次返回已就绪
- **THEN** 前两次保存等待结果且不调用工作模型，第三次按条件策略携带就绪信息请求目标 thread 执行

#### Scenario: SSH 工作区的脚本检查
- **WHEN** 任务属于远端工作区且脚本配置为该工作区执行
- **THEN** 检查发生在该工作区环境，脚本中的本机地址不得被解释为 Gateway 主机地址

#### Scenario: 检查脚本超时
- **WHEN** 脚本超过配置的检查期限
- **THEN** 运行记录显示超时及诊断，任务不因该失败投递成功续跑动作

### Requirement: 模型判断必须有明确结果与因果关联

模型判断 SHALL 支持自然语言条件，使用与工作 thread 职责分离的判断 thread，并返回等待、执行、完成或需要人工处理的明确决定及理由。系统 MUST 将本次判断绑定到触发、任务 revision、冻结输入和判断执行身份；无效输出、执行失败或超时不得伪装成等待或通过。同一任务 MUST 避免判断重入，判断 thread 的执行结束不得自行触发该任务的工作执行结束条件。

#### Scenario: 用自然语言判断上线条件
- **WHEN** 条件是“服务稳定且日志无数据库连接错误再继续”，判断 thread 收到本次服务信息与日志
- **THEN** 运行记录保存该次判断、理由和判断 thread 引用，仅执行决定才能触发目标工作动作

#### Scenario: 判断执行结束事件
- **WHEN** 判断 thread 返回等待并产生执行结束事件
- **THEN** 任务按原触发策略等待，不因自己的判断结束立即再次判断

#### Scenario: 判断期间任务已修改
- **WHEN** 判断开始后用户修改任务定义，旧 revision 的判断随后返回执行决定
- **THEN** 系统保留旧判断记录但不得按过期配置投递新动作

### Requirement: 上下文发布与执行请求必须可分别选择

动作 SHALL 支持仅发布上下文与发布上下文后请求目标 thread 执行，并明确事件内容或可更新状态的语义。上下文 MUST 经现有唯一 owner 持久化，执行 MUST 经现有准入与队列投递。内部任务通知 MUST 保留来源，不得伪造真实用户 Turn；已发送的模型请求不得被追改。投递时机 MUST 显式记录，默认当前执行结束后投递。

#### Scenario: 只更新服务状态
- **WHEN** 空闲 thread 关联任务配置为仅更新上下文，服务状态发生变化
- **THEN** 状态被持久化但不产生模型执行请求，界面区分已保存与已被模型消费

#### Scenario: 工作 thread 正忙
- **WHEN** 满足条件的通知要求在当前执行结束后继续，而目标 thread 正在执行
- **THEN** 系统持久接受并按既有串行队列投递，记录等待原因，不并行启动同一 thread

#### Scenario: 更新同一状态来源
- **WHEN** 多次检查产生同一服务的新状态
- **THEN** 系统按同一来源的 revision 更新当前状态，不将无变化的轮询结果重复注入模型，也不覆盖已提交历史事实

### Requirement: 任务生命周期必须独立于单次执行

系统 SHALL 分别展示任务生命周期、当前运行阶段、原因及下次触发。任务 MUST 支持暂停、恢复和终止；暂停后不得发起新的自动动作，但不得隐式取消已接受执行。一次动作接受后结束、工作执行完成后结束或持续周期运行 MUST 由任务策略明确，单个 Job 完成不自动等同任务完成。

#### Scenario: 暂停正在等待条件的任务
- **WHEN** 用户暂停任务，随后旧检查结果返回条件满足
- **THEN** 任务保持暂停并保存检查记录，不产生新的续跑动作

#### Scenario: 暂停已接受工作的任务
- **WHEN** 目标工作执行已经被接受后用户暂停任务
- **THEN** 系统停止后续自动调度，现有执行保持可观察，取消该执行须通过明确的执行控制

#### Scenario: 一次性等待与周期任务
- **WHEN** 一次性服务等待任务完成配置的动作，而另一周期任务完成一次执行
- **THEN** 前者按结束策略完成，后者继续等待下一次计划，界面能区分两者

### Requirement: 重复触发与重启必须恢复同一进度

任务 MUST 持久保存触发标识、定义及输入 revision、判断结果、动作幂等身份、投递回执及执行引用。相同事件重试 MUST 复用同一运行和动作；相同幂等键不同内容 MUST 明确冲突。系统 SHALL 支持首次满足、状态由不满足变满足以及每次满足等显式策略；后端重启后 SHALL 恢复已启用任务并按补跑策略对账，不要求用户打开会话。无法确认的外部副作用 MUST 显示中断或结果未知，不得盲目重放。

#### Scenario: 连续轮询服务已上线
- **WHEN** 任务配置首次满足且服务连续三次检查均已上线
- **THEN** 只产生一次续跑动作，重启后也不因丢失内存标记再次触发

#### Scenario: 动作接受后未写回任务进度就重启
- **WHEN** 目标已持久接受动作而任务运行记录尚未收到回执时后端退出
- **THEN** 恢复使用原身份查询或重投，关联同一接受结果，不创建第二次工作执行

#### Scenario: 外部通知重复或冲突
- **WHEN** 外部脚本重发相同幂等键的通知
- **THEN** 相同内容返回原接受结果，不同内容返回明确冲突，不重复执行

#### Scenario: 后端停止期间错过检查
- **WHEN** 任务所属工作区后端停止后重新启动
- **THEN** 系统按配置跳过、执行最近一次或补跑，展示实际恢复结果，不宣称停机期间已执行检查

### Requirement: 启动就绪与任务恢复进度必须分离

工作区启动 SHALL 等待统一任务运行时的存储、事件订阅、调度所有权与受管理恢复 worker 初始化成功，不得等待逐项任务检查、脚本或模型执行完成。任务 SHALL 由统一运行时在后台按持久状态恢复，恢复进度与失败 MUST 可查询；同一任务完成在途对账前新触发必须持久排队，不能重复执行。Goal 与其他任务 MUST 使用相同恢复入口，不再单独挂接 Goal 启动调度。运行时初始化失败 MUST 使启动失败；worker 运行期失效 MUST 被生命周期 owner 感知并显示调度失败，不得继续报告任务运行时健康。

#### Scenario: 某个 Goal 恢复很慢
- **WHEN** 工作区启动，统一任务运行时初始化完成，但某个 Goal 恢复或条件判断仍在等待
- **THEN** 工作区可完成就绪并提供界面，任务显示恢复进度，其他已恢复任务可推进，不要求先打开会话或等待该 Goal 完成

#### Scenario: 恢复期间收到新事件
- **WHEN** 某任务仍在对账旧动作，此时收到相同执行结束事件或新计划点
- **THEN** 触发被幂等持久接受并在该任务恢复完成后处理，不越过对账创建重复动作

#### Scenario: 恢复中的任务被暂停
- **WHEN** 用户暂停仍在恢复的任务，之后恢复工作继续推进
- **THEN** 恢复尊重最新 revision 与暂停状态，不以启动时读到的 active 状态发起新动作

#### Scenario: 统一 worker 初始化失败或运行期退出
- **WHEN** worker 未能初始化，或初始化成功后发生未处理异常而退出
- **THEN** 前者使工作区启动失败，后者明确报告运行时调度失败，均不得显示所有任务已恢复或静默丢弃待处理任务

### Requirement: Goal 必须作为统一任务运行时的内置应用

Goal SHALL 通过统一组件构建，并保留主线程限定、目标内容、既有状态、预算记账、模型完成声明、激活和目标更新、执行事件续跑及启动恢复行为。Goal 工具、API 与专用视图 MUST 操作同一权威任务，不再维护独立可变 Goal 状态或专用调度链路。

#### Scenario: Goal 与普通条件任务共存
- **WHEN** 用户分别创建主线程 Goal 与脚本条件任务
- **THEN** 两者通过同一持久任务运行时管理，脚本任务不需要伪建 Goal，child thread 也不因此获得 Goal 能力

#### Scenario: 多事件指向同一 Goal 执行结束
- **WHEN** Agent 结束与 Job 完成等事件先后到达
- **THEN** 系统按既有 Goal 业务语义记账并幂等续跑，不因统一抽象重复投递或漏掉激活恢复入口

#### Scenario: Goal 不再拥有独立恢复调度
- **WHEN** 工作区启动或关闭，且其中存在 Goal 和其他类型持久任务
- **THEN** 只有统一任务运行时负责恢复、事件调度与停止准入，Goal 仅提供应用规则，不通过独立服务或转发包装层保留另一套生命周期入口

#### Scenario: fork 创建独立 Goal
- **WHEN** 用户沿现有公开fork入口请求为新Session main创建独立Goal
- **THEN** 新任务沿同一创建journal幂等安装，保留冻结目标与指定预算，使用新Goal身份和目标冻结创建时刻，用量及逐Job续跑标记从零开始；发布前不得被任务worker调度，取消与重启沿原创建状态收敛
- **AND** 同Session child创建不取得Goal，旧goal.json物化检查随任务owner迁移，不要求新旧两份Goal事实并存

### Requirement: 迁移必须形成单一生产链路

系统 MUST 一次性导入既有 Goal 与 Gateway 生成器，保留稳定身份、预算、状态、计划游标、已触发标记及未完成运行引用。生成器 MUST 按原执行工作区解析归属；缺失或离线目标必须显示未完成迁移，不得默认改绑。成功切换后 MUST 删除旧生产调度、读写及接口并迁齐消费者，旧数据只作显式迁移或备份输入。

#### Scenario: 重复执行迁移
- **WHEN** 导入过程中断后再次运行迁移
- **THEN** 已导入对象按原身份复用且不重复调度，只有核验通过的 owner 才开始统一运行

#### Scenario: 旧任务的工作区离线
- **WHEN** 某 Gateway 生成器无法完成目标工作区导入
- **THEN** 系统报告具体任务与原因，不把任务丢入默认工作区，也不同时启用新旧调度
