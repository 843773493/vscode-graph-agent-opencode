# background-maintenance Specification

## Purpose

作为既有资源管理的一部分，通过可独立使用的 Node／Python 插件 SDK 统一进程内后台维护调度、失败报告与异步关闭行为，同时保留各资源及数据 owner 对引用、保留策略和实际释放的唯一决定权，避免源码依赖、清理永久停跑或第二套资源管理体系。

## Requirements

### Requirement: 后台维护调度属于资源管理的进程内公共能力

系统 SHALL 由 Workspace Backend 按工作区、插件按运行实例在本进程装配 SDK 后台维护调度，调用原负责模块的维护入口，不作为独立进程、对外服务或 Gateway 的中央回收控制面。Gateway SHALL 保持插件进程的启动、接管、停止及退出核实职责，插件 SHALL 保持内部运行资源的管理职责，Backend SHALL 保持工作区业务关联和本地数据的管理职责。系统 MUST NOT 为统一维护新增通用远程回收 RPC、广播释放命令，或要求每个服务建立独立常驻生命周期管理模块。

#### Scenario: 后端检查导致远端资源需要释放

- **WHEN** Backend 的维护调度调用本地资源负责模块，并由其确认某插件资源符合原回收条件
- **THEN** 该负责模块沿已有业务传输与 Gateway 路由执行具体操作，插件释放内部资源，原负责模块核实结果；调度本身不向所有服务发送通用释放请求

#### Scenario: 插件执行自己的内部清理

- **WHEN** 插件内部截图或历史文件需要按原策略清理
- **THEN** 插件沿自己的既有入口执行，不依赖本次 Backend 维护调度发送通知；Gateway 不读取工作区业务数据代为判断

#### Scenario: 后端连接或维护检查失败

- **WHEN** Backend 的连接断开或一次维护检查失败
- **THEN** 保持原资源保留及进程生命周期规则，不因该调度新增自动停止插件进程的动作，也不把失联直接视为资源已释放

### Requirement: 插件可通过独立 SDK 公开入口使用公共能力

系统 SHALL 为 Node 和 Python 插件提供可独立安装的 SDK 包，公开实例管理接入、命令、日志、诊断和轻量后台维护能力，保留原管理 HTTP 合同。插件 SHALL 能只依赖 SDK 及其声明依赖使用上述能力，不依赖产品 `app/`、客户端、具体内置插件或仓库路径。公开类型与运行时协议 SHALL 来自同一权威合同生成链，不手写平行合同或从客户端私有目录导入。已迁入的公共能力 SHALL 只有一份实现，原产品消费者直接迁至公开入口，不保留旧入口转发和回退导入。

#### Scenario: 独立 Node 插件消费 SDK

- **WHEN** 插件从 SDK 公开包入口加载实例管理与周期调度，并执行真实类型检查和启动
- **THEN** 公开类型及运行依赖在包内或声明依赖中完整解析，不需要 Web 客户端的类型、构建输出或源码目录

#### Scenario: 独立 Python 插件消费 SDK

- **WHEN** 插件在无产品模块和仓库 pythonpath 的环境导入已构建的 SDK 包
- **THEN** 能建立原管理入口、执行本地维护回调并完成异步关闭，不通过复制 `app/` 文件或动态查找产品源码补依赖

#### Scenario: Backend 与插件共享 Python 维护能力

- **WHEN** Backend 和 Python 插件使用后台维护调度及必要进程内生命周期能力
- **THEN** 依赖同一 Python SDK 实现，保留资源释放顺序、取消保护及失败资源重试，统一补齐任务终态错误结算，不在产品目录另存第二个调度器或 scope

#### Scenario: 只导入轻量公开能力

- **WHEN** 无插件启动环境、无运行中事件循环的进程导入 SDK 根入口、维护或 Python 生命周期模块
- **THEN** 导入成功且不读取实例／日志去向配置、不启动后台操作、不注册信号，不传递加载 HTTP 管理或诊断重依赖；显式初始化管理能力时仍报告缺失或非法配置

### Requirement: SDK 与产品使用同一请求身份上下文

Python SDK 与产品 SHALL 共享同一轻量 request_id 上下文及请求 state 读取能力，消费者直接使用其公开入口，不复制 ContextVar、不提供可替换 getter 或回退 ID。上下文模块 SHALL 只依赖标准库；HTTP 依赖 SHALL 保留框架可解析的真实类型，并与轻量入口隔离，不反向加载 runtime／commands。产品中间件 SHALL 继续负责入口请求身份的接受／生成、绑定／恢复与响应头；Gateway／actor 鉴权仍归原产品 owner。Node SHALL 沿原显式参数传递 request_id，不为此新增异步上下文系统。

#### Scenario: 并发请求经 SDK 命令与日志消费身份

- **WHEN** 两个携带不同 request_id 的真实请求并发进入产品中间件并调用 SDK 能力
- **THEN** 命令与日志分别使用本请求的原 ID，嵌套绑定退出后恢复前值，缺失必需身份明确失败；不生成第二个 ID，也不串到另一个请求

### Requirement: Python 生成协议只有一个真实包归属

Python SDK SHALL 完整交付现有 Python 生成协议的真实顶层 `boxteam` 包；Backend、SDK 与插件 SHALL 使用同一标准导入及生成定义。生成工具 SHALL 直接输出到 SDK 所拥有的包，迁齐消费者后 MUST 删除旧产品生成目录和模块别名注入，不维护另一份同名协议、按导入顺序选实现或增加第三个协议安装包。SDK 包初始化 MUST 保持按需导入，不加载全部协议。

协议生成及生成产物 check SHALL 独立于应用导入与 SDK 安装；check MUST NOT 安装依赖或回写源码／环境。需要 Backend 的原 HTTP／OpenAPI 合同检查 SHALL 在本次协议生成、当前 SDK 构建及正常依赖安装完成后执行，使用本次 descriptor 与实际安装的 SDK（开发可 editable，制品验收用 wheel）；原构建／CI 调用方 MUST 保留这道必需校验，不以纯生成通过替代。

#### Scenario: 产品与 SDK 以不同顺序导入协议

- **WHEN** 分别先导入 SDK 再导入产品、先导入产品再导入 SDK，并操作同一种协议消息
- **THEN** 使用同一实际模块及 descriptor，实际序列化与反序列化保持原 wire 合同，无别名注册或重复加载

#### Scenario: 已安装 SDK 落后于新增协议

- **WHEN** 已有环境仍安装旧 SDK，而新 Backend 已消费本次新增的协议类型
- **THEN** 不导入应用即可生成当前协议；原构建链构建并正常安装当前 wheel 后再校验应用合同，真实类型与本次 descriptor 一致，不需要先让旧 SDK 成功加载新应用，也不通过源码路径兜底

#### Scenario: 只检查生成产物

- **WHEN** 执行协议生成产物 check 且仓库产物与当前 proto 不一致
- **THEN** 明确失败且不导入 Backend、不安装 SDK、不修改生成文件或运行环境；一致时通过仍不能替代后续应用合同校验

### Requirement: 日志静态合同随 SDK 分发且配置状态保持唯一

SDK SHALL 随包提供从唯一源构建的日志静态合同，沿原格式版本和日志行为运行，以包资源定位而非工作目录或产品源码定位。日志目标、请求身份与可热应用状态 SHALL 继续由原 owner 管理，不增加配置镜像或写入 SDK 包；资源缺失或版本错误 MUST 明确失败。

#### Scenario: 更换工作目录后初始化日志并热应用设置

- **WHEN** 独立制品在任意工作目录显式初始化日志，并经原管理入口热应用设置
- **THEN** 从 SDK 包资源加载与唯一源一致的合同，原实例的日志去向、revision 和 request_id 保持一致，不需要产品源码或第二套热配置

### Requirement: 插件发布制品自带 SDK 并可在仓库外离线使用

系统 SHALL 在构建阶段将锁定的 SDK 与生产依赖包含在可重定位的插件制品中；产品 Backend 制品 SHALL 同样包含其实际 SDK 依赖。安装及启动 MUST NOT 联网下载 SDK、执行依赖安装命令、依赖源码绝对路径、指向仓库的链接或 editable 安装路径。插件包仍 SHALL 使用原清单、目标运行时及目录／ZIP 安装发布合同，不增加安装器或隐式运行时 SDK 注入。

#### Scenario: 包内 SDK 归档通过真实安装入口

- **WHEN** 完整目录或其 ZIP 内携带已声明的 SDK tarball／wheel、包管理器生成的锁及预构建依赖
- **THEN** 同一安装规则核包内来源、原生摘要、名称、版本和实际依赖树后受理，不要求 SDK 存在于公网 registry；不放开目录、链接、editable、Git 或包外来源

#### Scenario: 归档与锁或声明不一致

- **WHEN** 包内 SDK 归档被篡改、缺失、越界，或其名称／版本／来源与声明、锁、实际依赖树冲突
- **THEN** 安装明确失败且不发布半成品，不跳过原完整性检查、不联网补依赖

#### Scenario: 同一 SDK 版本产生新的构建内容

- **WHEN** SDK 版本不变而新归档内容变化
- **THEN** 新归档使用内容摘要命名的包内路径，依赖声明与标准锁指向该路径；旧归档保持不变，不依靠覆盖同路径文件或清空包管理器缓存选中新版

#### Scenario: 仓库外离线运行完整插件包

- **WHEN** 完整 Node 或 Python 插件制品解包到独立目录，子进程没有产品源码导入路径且无法联网获取依赖
- **THEN** 插件完成原管理握手、一个真实业务操作及正常停止，SDK 和全部必要运行依赖均从制品解析

#### Scenario: 产品 Backend 依赖 Python SDK

- **WHEN** 从完整产品制品启动 Backend 而非从源码目录启动
- **THEN** 原工作区初始化与维护调度能解析随产品携带的 Python SDK，不依赖开发机已安装的本地包

### Requirement: 开发与 release 运行同一构建结构的完整插件目录

开发与 release SHALL 共用一个完整目录构建流程及同一依赖声明、标准锁和依赖校验；开发加载构建目录，release 只封装该目录为 ZIP，不在最后一步替换依赖或追加缺失资源。插件制品开发 MUST NOT 通过源码路径、workspace 链接或 editable 运行 SDK。插件制品中的 SDK 改动 SHALL 重建归档、更新对应锁来源及摘要；只改插件业务代码 SHALL 复用未变化依赖。开发版本 SHALL 依据实际组装有效载荷派生，输入指纹仅用于缓存，不以相同输入豁免实际内容差异。更新 SHALL 先发布完整不可变制品，再显式提交所选配置绑定的版本，由原配置生命周期交接实例，不覆盖运行目录或重启无关绑定。

#### Scenario: 同一目录分别用于开发和 ZIP 验收

- **WHEN** 同一完整构建目录分别通过目录受理和 ZIP 安装在隔离环境启动
- **THEN** 有效载荷、相对路径、SDK 加载来源及真实业务行为一致，ZIP 阶段没有独立安装或依赖替换；两种制品摘要按原各自合同核实

#### Scenario: 同一 Home 改用另一交付形式

- **WHEN** 同一 Home 已安装某包版本，又以相同包身份及版本提交不同原制品摘要，包括相同有效载荷的目录与 ZIP 双向切换
- **THEN** 沿原不可变版本合同拒绝，原制品与绑定不变；不通过新增有效载荷摘要、自动卸载重装或来源 fallback 放行，更换制品沿原显式新版本安装与绑定更新流程

#### Scenario: 重复安装原来源同摘要制品

- **WHEN** 同一 Home 再次提交相同包身份、版本及原制品摘要
- **THEN** 沿原安装幂等行为受理，不改写原制品或绑定，不把目录与 ZIP 的有效载荷相同视为原制品摘要相同

#### Scenario: 修改 SDK 后重建并重启

- **WHEN** SDK 内容变化而开发软件版本未变，用户重建并显式重启受影响插件
- **THEN** 新归档与锁摘要一致且实际加载新 SDK；原包版本不可被不同内容覆盖，实际启用绑定指向已发布版本，禁用状态及其他实例不受影响

#### Scenario: 相同源码输入在独立构建中产生不同内容

- **WHEN** 两次开发构建的源码输入相同但最终依赖或资源字节不同
- **THEN** 实际内容差异产生不同开发包版本，不错误复用相同输入指纹对应的包身份；版本派生不引用自身最终摘要或 ZIP 时间戳

#### Scenario: 更新绑定版本与新工作区默认项

- **WHEN** 用户显式应用某 Gateway／工作区下具体插件绑定的新版本
- **THEN** 原配置 owner 仅修改该绑定版本，保留 enabled、范围和参数，由原 reconcile 交接实例；不以易失 instance_id 作为配置主键，不自动更新新工作区默认项或其他绑定；原配置冲突明确返回，不自动覆盖

#### Scenario: 只修改插件代码或重建失败

- **WHEN** 依赖输入未变而只修改插件代码，或新构建在完成前失败
- **THEN** 前者不重复准备依赖；后者不发布半成品、不破坏当前运行目录，也不以运行时补装完成失败构建

### Requirement: 后台维护沿原 owner 清理并保持资源归属

系统 SHALL 由资源或数据所属 owner 判断回收资格并执行清理；维护调度 MUST NOT 维护另一份资源、引用、租约、保留期限或删除状态。即时删除、Thread 释放、插件停止和原启动一致性恢复 SHALL 保持原入口、错误与核实语义，不等待周期维护代办。Gateway MUST NOT 为此读取工作区业务存储。

#### Scenario: 回收与业务占用并发

- **WHEN** 周期检查发现一个候选资源，但原 owner 核实它仍有有效关联、租约或消息引用
- **THEN** 维护通过原 owner 保留该资源，不绕过其锁或以扫描快照直接删除

#### Scenario: 无 Thread 关联的工作区资源

- **WHEN** 工作区保留的 Browser 资源长期没有 Thread 关联
- **THEN** 维护遵守原工作区保留范围，不按临时资源孤儿规则删除

#### Scenario: 启动恢复发现业务不一致

- **WHEN** 必须完成的原启动恢复报错
- **THEN** 系统保留原启动失败与详细错误，不把它转换为可忽略的维护失败后宣告业务就绪

### Requirement: 固定任务独立执行且不重入不补跑

系统 SHALL 按工作区或插件运行实例装配固定维护任务，每项任务在同一所属范围最多一个执行在途。公开周期 SHALL 采用整数毫秒，范围为 1 至 2147483647，布尔值不作为整数接受。一次执行成功或失败后 SHALL 再等待其正常周期，不累积、并发补跑或立即重试错过的周期；慢任务 MUST NOT 通过一个共享串行等待队列阻塞其他任务。重复任务注册 MUST 明确失败，不能产生第二个循环。

#### Scenario: 静态集合中后项无效

- **WHEN** 任务集合包含重复或空标识、非法毫秒周期、错误首次策略或不可调用回调
- **THEN** 在创建任何循环前拒绝整个集合，不试执行回调验证，不留下部分启动任务；同一所属范围的重复启动仍由原生命周期拒绝

#### Scenario: 执行时间长于周期

- **WHEN** 某维护回调尚未结束且已经超过一个或多个周期
- **THEN** 同任务保持单次执行，结束后等待一个正常周期，不启动并行副本或追赶积压执行

#### Scenario: 两个工作区同时维护

- **WHEN** 同一后端进程挂载两个工作区并启动各自维护
- **THEN** 每次回调使用所属工作区的 owner，关闭其中一个工作区不停止另一个工作区的任务

#### Scenario: 同一插件的两个运行实例

- **WHEN** 同一插件在两个工作区各有一个运行实例并注册同名维护任务
- **THEN** 两个实例分别执行本地回调，停止一个实例的调度不停止另一个实例，也不共享可变清理状态

### Requirement: 单次维护失败不永久中止其他任务

系统 SHALL 在单次维护异常时明确记录所属工作区／插件实例、任务身份、耗时和原错误堆栈；其他维护继续执行，失败任务只在下一正常周期重新扫描。系统 MUST NOT 伪造成功、修改清理资格、自动重建数据或用快速重试掩盖错误。取消与进程终止信号 MUST 保留原语义。

仅在调度仍开放时，普通回调错误 SHALL 进入周期失败处理；停止期间出现的真实存储／回调错误 MUST 交给该次关闭调用，不能只因已请求取消而吞掉或转为正常终止。

#### Scenario: 活动清理失败而附件到期

- **WHEN** 本轮活动事件清理失败，同时存在满足原回收条件的未发送附件
- **THEN** 活动清理错误可查，附件仍由其 owner 正常回收；活动任务在下一正常周期再次尝试

#### Scenario: 回调收到关闭取消

- **WHEN** 工作区关闭取消正在执行的维护回调
- **THEN** 系统不把取消当作普通异常后继续调度下一周期，不产生新的维护调用

### Requirement: 关闭维护须先于依赖释放并等待原写入结算

工作区关闭 SHALL 先禁止新维护执行并停止等待中的周期，再排空已经开始的回调，最后关闭其数据库、资源 owner 与传输依赖。已开始的不可抢占写入 SHALL 沿原持有链等待结算；失败 MUST 沿原关闭流程报告，不宣称已关闭或把在途操作遗弃为无 owner 后台任务。维护 MUST NOT 引入第二套 scope、关闭恢复账本或额外强杀协议。

#### Scenario: 关闭时 SQLite 写入仍在执行

- **WHEN** 维护已开始真实 worker 写入，此时工作区请求关闭
- **THEN** 依赖保持有效直到写入结算，之后继续原关闭流程；期间不启动新周期

#### Scenario: 取消后出现迟到存储错误

- **WHEN** 原写入在关闭取消后返回存储错误
- **THEN** 原异常沿关闭链可见，系统不报告依赖已成功释放，不仅记录取消而丢失存储错误

#### Scenario: 已结束任务的错误在关闭时结算

- **WHEN** 维护任务已结束并失败，首次关闭收集其结果后用户再次显式请求关闭
- **THEN** 首次关闭完整返回该错误并保持失败；已结算终态任务不重放、不永久阻塞下一次关闭，后者仅处理仍未完成的资源／子 scope，真实释放失败仍可继续报告。历史失败结果不被改写，也不增加单独的错误确认接口或消费账本

#### Scenario: 周期到期同时关闭或关闭等待者被取消

- **WHEN** 关闭与周期到期竞争，或多个调用方等待关闭而其中一个被取消
- **THEN** 已禁止新执行后不再进入回调，其他等待者共用本次排空结果；取消等待者不遗弃在途收尾，回调晚于取消返回也不开始下一周期，失败后显式再次关闭不永久复用已结算的失败结果

### Requirement: 本次接入保持原周期与清理资格

系统 SHALL 将活动事件、配置事件、HTML 快照、未发送附件和上下文详情五项小时级清理独立调度，首次周期执行保持在启动周期任务一小时后；Browser 孤儿检查 SHALL 保持首次立即及随后每秒检查。原启动清理 SHALL 保持原依赖位置且不因接入再执行一遍。本次 MUST NOT 改变保留期限、已接受附件保护、配置事件连续后缀及上下文引用规则，也不新增 terminal steering 内孤儿检查的第二调用方。

#### Scenario: 正常启动后的首次调度

- **WHEN** 工作区完成原启动流程并装配周期维护
- **THEN** Browser 按原时机开始检查，小时级任务不批量抢先运行；业务就绪不等待周期回调完成

#### Scenario: 清理候选中包含已发送附件和被引用详情

- **WHEN** 原 owner 扫描到到期草稿、已接受消息附件和仍被 sealed／lineage 引用的详情
- **THEN** 仅回收符合原条件的草稿，消息附件及被引用详情保持可读

#### Scenario: 原配置状态仍引用历史事件

- **WHEN** 配置事件按期限清理但 pending candidate 的诊断仍引用某事件
- **THEN** 原 owner 保留必要的连续事件后缀，维护不制造游标窗口中的缺口

### Requirement: 插件周期维护与事件清理及关闭分别执行

Browser 插件 SHALL 使用 Node SDK 在后台首次立即清理截图，随后按原每小时周期调用同一原清理入口；单次失败记录并在下一正常周期再检查，不新增启动就绪阻塞或重复首次清理。Terminal 插件 SHALL 保留启动及原操作边界的历史清理，不因提供 SDK 调度而新增周期任务。插件关闭 SHALL 停止调度并等待在途清理结算，再释放其依赖，异步收尾 MUST 可被等待，不能用同步 dispose 返回代替排空。显式 stop、delete、shutdown 和卸载 MUST NOT 延后到周期维护。

#### Scenario: Browser 周期清理失败后继续检查

- **WHEN** Browser 本轮截图清理失败，之后错误解除且下一个正常周期到达
- **THEN** 原错误可查，SDK 再次调用原清理入口；保持单次在途，不立即重试，不启动第二循环

#### Scenario: Terminal 事件触发清理

- **WHEN** Terminal 插件通过 SDK 建立公共管理入口并进入原启动或创建操作
- **THEN** 原历史清理在原边界执行，原资格与保留数不变，不出现新增定时清理循环

#### Scenario: 插件关闭时清理仍在执行

- **WHEN** 插件收到关闭请求且已有 SDK 维护回调在执行
- **THEN** 调度停止新执行并等待回调结算，依赖在此期间保持可用；错误按原关闭链报告，管理 accepted 回执仍不代表进程已退出

### Requirement: 后台维护不得扩大普通交互的内部成本

系统 SHALL 保持维护与普通读写请求独立，不把维护扫描或全库完整性检查串入普通请求。维护竞争时的普通暖 API 完整响应 SHALL 遵守既有 p95≤500ms、单次≤1500ms 预算；已有更严格要求仍有效。计时 SHALL 包括 Gateway 路由、内部排队、锁等待、校验与序列化直到完整响应，不以加载占位、平均值或测试进程超时代替。

#### Scenario: 真实维护在途时的并发正确性

- **WHEN** 测试装具在真实维护 worker 已开始的现有 I/O 边界设置屏障，期间经 Gateway 读取同一存储，随后释放屏障并等待 owner 完成
- **THEN** 正常读取、有效记录及原引用保护保持正确，清理完成后结果一致；业务 owner 与 SQL 真实执行，屏障仅控制测试时序，不加入生产配置或性能样本

#### Scenario: 固定并发负载下的真实延迟

- **WHEN** 隔离工作区固定执行 3 批，每批 10000 条真实候选、100 条有效对照、一次真实 owner 清理及 20 次经 Gateway 访问同一存储的并发暖分页请求
- **THEN** 采集阶段在进程外 60 秒硬超时内保留全部 60 次请求及 owner 区间、原始时长、p95、max、响应大小和 request_id，按全部样本核原预算且有效对照记录未被错误清理；单列实际重叠次数与样本，不以最少重叠次数判定预算通过，也不把无重叠结果或正确性屏障冒充竞争延迟证据；禁止用屏障、sleep／mock 慢回调或人工占锁制造性能重叠，禁止自动加数据、补批、调参、失败重试或删除慢样本。并发正确性与延迟分别报告，任一业务正确性或预算失败均不得宣告验收通过

### Requirement: Thread 闲置扫描复用调度且保留原 owner

AgentExecutionService SHALL 将 Thread 闲置扫描的周期触发注册到 Python SDK，启动时仍等待一次原检查，随后每次检查结算后等待 60 秒；任务 SHALL 使用空执行上下文；维护任务存活 MUST NOT 作为 Job 准入条件。SDK SHALL 按注册顺序返回 scope 持有的原任务供观察，关闭仍通过唯一 scope 完成。ThreadResidencyTracker SHALL 独占准入、blocker、generation、30 分钟闲置阈值及卸载判断，不增加第二个扫描调用方或资源事实源。

#### Scenario: 启动检查失败后正常周期重试

- **WHEN** 首次检查或后续周期扫描中的原资源释放失败
- **THEN** 原错误可查，失败 owner 保留并在下个正常 60 秒周期重试；重复 start 不创建第二任务，其他工作区不受影响

#### Scenario: Thread 扫描关闭未结算

- **WHEN** 原 runtime.shutdown 等待扫描期间，观察者被取消或等待超过原 30 秒期限
- **THEN** 保留唯一关闭任务、原扫描句柄、缓存和依赖，不重启或重复取消扫描；原扫描结算后再释放依赖，迟到错误沿关闭链交付后仅允许显式重试剩余关闭

#### Scenario: 关闭准入与维护 scope 关闭之间的竞态

- **WHEN** Agent owner 已请求关闭，维护 scope 尚未开始关闭，同轮事件循环唤醒周期任务或返回在途扫描错误
- **THEN** 不开启新的扫描，在途原错误仍沿关闭链交付；不因 scope 暂时开放而记录“下周期重试”后返回关闭成功

#### Scenario: 维护任务意外退出后接受新执行

- **WHEN** 原维护任务意外取消或因调度异常退出，之后收到用户消息或内部执行，而 owner 及实际执行资源仍可用
- **THEN** 维护故障独立可查，新 Job 沿原 runtime 构建或复用链正常执行；不因维护退出标记失败或用户取消，不自动重启维护。owner 正在关闭时仍拒绝新 runtime admission，真实用户取消和原维护关闭错误仍沿原入口处理

#### Scenario: 新活动阻断闲置卸载时接受同代执行

- **WHEN** 新 runtime admission 正在等待已有闲置卸载，而卸载在线性化前因新增调试或后台活动 blocker 撤回
- **THEN** admission 重新检查 owner、generation 及 scope 后复用可用的同代 runtime，不因该撤回失败或重复构建；需要换代时仍由原 blocker 阻止卸载，真实资源释放错误仍交回等待者

### Requirement: Backend 开发可用标准 editable 安装且不改变发行独立性

Backend 本地开发 SHALL 通过 uv 的 `sdk/python` editable 来源安装 Python SDK，不手改导入路径；普通 SDK 源码修改 MUST NOT 要求重建 wheel、修改版本或更新锁。SDK 元数据版本 SHALL 从根软件版本同步；包内日志合同 SHALL 从唯一源生成并校验，干净 checkout 的标准安装必须完整可用。发行环境 SHALL 正常安装 wheel，产品依赖导出保留锁定依赖及摘要，以当前 SDK wheel 替换本地 editable 项；插件制品来源规则不变。

#### Scenario: 安装后修改 SDK 源码

- **WHEN** 开发环境完成标准 editable 安装后修改 SDK 源码，并从仓库外工作目录启动新的 Python 进程
- **THEN** 无需重新安装即可加载修改后的实现，包内日志合同可用，依赖锁不因普通源码变化而更新

#### Scenario: 制品不再能访问开发源码

- **WHEN** 产品从当前 SDK 导出带摘要的 wheel 依赖，完成正常安装后开发源码目录被移走
- **THEN** 实际 SDK 和日志资源仍从已安装制品加载，依赖中没有 editable 或开发目录链接

#### Scenario: 生成日志资源过期

- **WHEN** SDK 包内生成日志合同与唯一源不一致
- **THEN** 只读准备检查明确失败且不回写，显式准备后两者一致

### Requirement: 仓库内 Node 产品开发使用标准 workspace 且发行保持独立

仓库内 Node 产品消费者 SHALL 通过 Bun workspace 解析 `sdk/node` 的公开包入口，普通 SDK 源码编辑 MUST NOT 要求重建 tarball、修改版本或更新锁。准备入口 SHALL 同步版本、workspace 声明及包内生成日志资源，check MUST NOT 构建 SDK 或回写文件。产品发行 SHALL 沿原独立运行时清单安装包内 tarball，不携带开发 workspace 链接；插件制品继续遵守独立构建与安装规则。

#### Scenario: workspace 安装后修改实现

- **WHEN** 标准 Bun workspace 安装完成后修改 SDK 源码，并从仓库外工作目录运行消费者的新 Node 进程
- **THEN** 同一 TS 源码经开发构建或 watch 转换后，公开运行入口解析到 workspace 的 JS 产物，类型解析到当前 TS 源码；无需重新安装或修改锁即可读取改动，包内日志资源可用

#### Scenario: 发行运行脱离 workspace

- **WHEN** 原产品构建入口生成独立运行时清单、安装包内 SDK tarball，随后开发源码被移走
- **THEN** Node 消费者及日志资源仍从发行依赖目录加载，清单没有 workspace 声明或源码目录来源

### Requirement: Node SDK 单一 TS 源码分离开发编译与发行校验

Node SDK 的手写实现与公开类型 SHALL 统一维护在 TypeScript，不保留手写 JS／声明双轨。标准开发安装 SHALL 准备运行 JS，watch SHALL 增量转换且只在成功产物实际变化后触发更新；独立严格类型检查 SHALL 使用同一 tsconfig。发行构建 SHALL 严格检查并由同一个 TypeScript Program 生成 JS／声明，再发布到空输出；归档的输入指纹与编译 SHALL 使用同一份冻结内容，不重新读取可变 checkout。独立包 MUST NOT 依赖仓库源码、workspace 链接或开发编译工具。开发插件 SHALL 保留不可变归档及原安装合同，可跳过声明生成，但不得声称通过发行类型验收。

#### Scenario: 修改后快速编译与错误恢复

- **WHEN** SDK watch 观察到 TS 或包内资源变化，随后出现语法错误并被修复
- **THEN** 成功修改更新产物，语法错误保留上次可用产物且不触发成功更新，修复后恢复；新增及删除入口、深层资源与空目录中的后续新增文件同步生效，相同产物不重复写入或重启

#### Scenario: 类型错误与发行独立性

- **WHEN** 开发源含可转换但类型错误的表达式，或发行包在源码被移走后由真实 Node 与 TypeScript 消费
- **THEN** 开发转换无需等待类型检查，独立检查明确拒绝类型错误；发行包的运行实现和生成声明均可独立解析

#### Scenario: 原开发启动入口自动准备 SDK

- **WHEN** 用户通过原开发入口启动实例，包括前后端源码分离的实例
- **THEN** 入口在加载 SDK 消费者前构建本次选定的前后端 SDK，同一根只构建一次；源码变化经原停止／启动流程生效，无变化不重复写产物，构建失败不启动服务；不要求用户额外运行编译命令或持久协调服务

#### Scenario: 停止、状态与原有实例归属

- **WHEN** SDK 正在编辑且含语法错误，用户查询状态或停止实例；或普通 start 复用已有实例、新建实例后就绪失败
- **THEN** 停止与状态查询不执行编译；已有实例沿原合同复用，不被启动失败清理；只有本次新建后失败才由创建 manager 清理，两份原异常均保留，不新增独占启动参数或产品 watch 管理链路

#### Scenario: 构建期间源码被继续编辑

- **WHEN** 发行编译已读取 TS 后源码发生修改，或归档编译前 checkout 发生修改
- **THEN** 本次 JS 与声明来自同一个 Program，归档来自参与本次输入指纹的冻结内容；后续编辑留给下一次构建
