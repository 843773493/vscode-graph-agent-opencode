# context-history-markers Specification

## Purpose

让用户在会话历史中以轻量标记发现实际参与模型请求的上下文文本，并在明确选择查看时读取当时的冻结正文。默认历史只传递有界元数据，不把 System Prompt 等来源改成普通消息，也不让正文体积拖慢会话加载。

## Requirements

### Requirement: 已派发上下文的轻量元数据

系统 SHALL 在原历史页面的 metadata 投影中提供实际派发请求选入且未作为普通消息完整展示的上下文文本标记，覆盖 System Prompt、工作区指引、Skill 及内部运行提示，包括 user/human 角色承载的内部注入片段。为生成标记 MUST 只查询有界索引元数据，不读取上下文正文、JSONL 或完整组装快照；原历史接口正常读取用户／模型消息不受此限制。不生成额外普通消息、Turn、活动计数或工具 schema 标记。普通上下文 MUST 不因 internal 或默认不展示而被禁止查看；本功能不新增保密分级、权限配置、审批或脱敏流程，已有内容接口的读取限制保持不变。返回的已知可用状态 MUST 不要求逐条读取正文或检查文件才能生成。

#### Scenario: 默认加载含大段 System Prompt 的会话
- **WHEN** 用户打开包含已派发 System Prompt、Skill 和运行提示的历史页
- **THEN** 页面获得来源身份、版本、顺序、长度、可用性及冻结引用，正文读取次数为零，未选入／未派发候选和工具 schema 不生成标记

#### Scenario: 普通内部上下文默认收起
- **WHEN** 普通 System Prompt 或工作区指引被标记为 internal，用户选择查看
- **THEN** 系统按精确引用读取冻结正文，不把默认隐藏变成读取禁令，不要求新增授权、密钥或审批

#### Scenario: 选入的 overlay 具有 backing 来源
- **WHEN** 请求选择了 overlay 引用，冻结正文由已有 backing contribution 支撑
- **THEN** 标记覆盖实际选入的文本且精确指向冻结正文，不遗漏 backing 支撑的来源，不把同一文本的 selection 和 backing 重复展示，也不展示未被使用的独立 backing

### Requirement: 标记遵守请求边界与版本变化

系统 SHALL 分别提供实际消费引用与展示锚点，保留封存选择顺序；不得伪造 canonical Item 坐标或修改模型实际输入顺序。首次派发使用的 System Prompt 和初始内部 user/human 注入 SHALL 合并为 transcript 起点标记，位于第一条真实用户消息之前；打断产生的提示实际被后续请求使用后，SHALL 位于该后续新用户消息之前、旧轮次已保留内容之后；同一 Turn 中更晚调用才引入的其它提示按对应调用边界定位。只有相同请求边界且相同展示锚点的来源才合并，同一来源版本持续使用不逐次重复，当前可见 lineage 首次使用、有效版本变化和重新引入产生标记。重试复用相同输入不重复，不同打断事件即使模板相同也不得合并为旧事件；完整请求详情仍能查看该请求全部来源。

#### Scenario: 首次上下文位于 transcript 起点
- **WHEN** 新建会话发送 U1，首个请求实际使用 System Prompt 与初始内部用户角色注入
- **THEN** 在回答仍运行时，初始虚线标记是 transcript 第一个内容成员，紧邻且位于 U1 上方；普通 U1 原文保持用户消息展示，标记中可按来源查看实际冻结的内部片段

#### Scenario: 打断提示在续发用户消息之前
- **WHEN** 用户打断运行中的首轮，再发送 U2，后续请求实际使用该次打断的 pending 提醒
- **THEN** 回答仍运行时按“旧轮次已保留内容→打断虚线标记→U2→新响应”排列，不把标记放到旧执行内部、U2 下方或新回答末尾，右键能查看该次打断提醒的冻结正文

#### Scenario: 不伪造尚未使用的打断上下文
- **WHEN** 用户已经打断，但提醒仍 pending，尚未被后续派发请求使用
- **THEN** 不将其展示成已使用上下文标记；后续实际派发并使用后按新用户消息上方的位置补入，不要求再次打断或刷新

#### Scenario: 连续使用和版本回退
- **WHEN** 来源按 A、A、B、A 被四个请求实际使用
- **THEN** 首次 A、变化到 B、变化回 A 分别产生标记，第二次连续 A 不重复；展示第二页不会把第二次 A 误判为首次

#### Scenario: 请求派发后失败且没有输出
- **WHEN** 某次请求已派发，但失败且没有生成 assistant Item
- **THEN** 标记仍有后端提供的有效请求边界，不因找不到下一条模型输出而消失或移到其它 Turn

### Requirement: 标记分页与历史视图一致

标记 SHALL 使用原历史查询的 scope、read snapshot 和 view revision，在原页预算内批量返回。超出标记预算 MUST 返回明确的元数据 continuation，不默默丢弃、不自动排空全部后续内容、不改变真实 Turn 分页。Fork、rewind 和隐藏历史成员 MUST 遵守选定 view 的可见性，正文引用保持历史 owner 绑定。

#### Scenario: 起点标记不复制到任意历史页顶部
- **WHEN** 用户只加载包含后续 Turn 的一页，再向前加载到真实起点
- **THEN** 初始标记只在真实起点所属位置出现一次，不作为常驻标题或每页开头重复；U2 所在页的打断标记仍紧邻且位于 U2 上方

#### Scenario: 来源较多并跨页查看
- **WHEN** 单页关联的上下文来源超过标记返回预算，用户继续加载来源元数据
- **THEN** 续页完整覆盖剩余可见标记且无重复，读取次数不随全部历史正文规模增长，原 Turn 页边界保持一致

#### Scenario: Fork 后原来源文件变化
- **WHEN** 用户打开 Fork 的继承历史，原工作区指引已修改或原 Skill 已卸载
- **THEN** 标记按 Fork 的冻结 view 显示，查看得到历史冻结版本，不读取当前来源文件

### Requirement: 仅明确菜单操作读取冻结正文

前端 SHALL 默认显示低干扰的居中虚线标记，通过原 Workbench 右键菜单及键盘菜单提供“查看上下文内容”和按需复制。悬停、获得焦点、打开菜单、选择来源或仅展开元数据列表 MUST 不读取正文；接受查看／复制后才定点读取。查看 SHALL 复用只读编辑器及原打开规则，正文不写入聊天历史缓存；一次打开不得因选择展示方式而预读后再次下载同一正文。

#### Scenario: 用户浏览标记但不查看
- **WHEN** 用户悬停标记、左键展开来源元数据并打开右键菜单后取消
- **THEN** 不发出任何正文请求，不插入提示词预览或大卡片，不改变模型上下文

#### Scenario: 用户从多个来源选择查看
- **WHEN** 用户通过右键或 Shift+F10 选中其中一个来源并接受查看
- **THEN** 仅请求该冻结引用的正文并在所属目标的只读编辑器展示；不读取同组其它来源，切换焦点工作区不改变读取目标

### Requirement: 历史正文准确性与明确读取边界

正文接口 SHALL 区分 canonical Item 与 request-only 快照贡献，沿原入口校验目标归属和历史引用，只读取所选正文及必要依赖，不引入独立权限判断链。来源冻结正文 MUST 与完整请求组装结果明确区分。缺失、损坏、目标不可用或原内容接口拒绝均明确返回原因，不回退当前配置或有界 LLM 日志；大小、取消和期限复用原内容接口机制，不静默截断后宣称全文，不为此扩建通用大文件处理框架。

#### Scenario: 查看合并 system 输入的一项来源
- **WHEN** 一个 system wire 输入由多个来源编译，用户只查看工作区指引
- **THEN** 返回该来源当时冻结正文，标注其来源语义，不把它冒充整个最终 System Prompt，也不恢复所有来源正文

#### Scenario: 正文不可用或超过展示上限
- **WHEN** 引用正文缺失或超过编辑器／内容接口允许大小
- **THEN** 用户看到对应明确原因和适用的既有操作，不承诺尚未实现的大文件功能，不看到当前配置替代品或伪称完整的截断文本

### Requirement: 实时标记与历史使用同一权威来源

系统 SHALL 在派发证据及元数据可读后，通过既有观察链路通知对应历史范围更新，由原 reader 返回标记；不得推送完整提示正文、新增常驻轮询或每标记订阅。即使 Turn revision 未变化，新派发元数据仍 MUST 可经原观察／历史 owner 更新，不等待 Turn 终态。实时响应合并 MUST 保留标记，刷新后与同一权威历史状态的结果一致；多 Tab 按各自 Thread／工作区隔离。服务提交派发事实到标记可见的暖态内部延迟 MUST≤2000ms、首次未缓存 MUST≤3000ms，不以等待模型输出或自动刷新替代。

#### Scenario: 新上下文在打开的会话内被消费
- **WHEN** 会话已打开，一个新版本指引被实际派发请求使用
- **THEN** 前端经原观察与历史更新链路得到一次标记，刷新后仍在同一位置，无需等待重新打开 Tab，其它 Thread 不出现该标记

### Requirement: 新建打断续发与历史恢复集成场景必须通过

本变更 SHALL 以真实 Workbench／Gateway／Backend 和原数据库完成“页面新建会话→Composer 发送 U1→运行中 UI 打断→Composer 发送 U2→右键查看→刷新→关闭会话 Tab 后重开”的集成测试作为完成门槛。上游模型可以使用确定性流式测试服务控制时序，业务 API 和历史／正文查询 MUST 不使用响应替身，不预写标记、不以直接调用提醒 helper 替代用户打断。测试 SHALL 同时核 DOM 相对顺序、真实冻结引用／正文、实际派发使用、上下文正文请求次数及实时／历史一致性；普通消息正文读取不计为内部上下文提前读取。单元测试、预置历史截图、构建或单独菜单测试均不能替代该场景。

#### Scenario: 实时新建打断续发并查看
- **WHEN** 测试从页面新建同一工作区的新会话，发送 U1 并控制上游保持执行中，通过 UI 停止确认实际取消，然后发送 U2 并确认后续请求使用打断提醒
- **THEN** 首次标记位于 U1 上方且包含测试实际注入的 System Prompt 与内部用户角色来源；打断标记在旧轮次已保留内容之后、U2 上方，均在对应回答仍运行时可见；悬停／打开菜单／取消不读上下文正文，接受查看后仅所选正文读取一次且与对应冻结来源全文一致；相同初始来源不在 U2 前重复展示

#### Scenario: 刷新与重开走真实历史路径
- **WHEN** 上述流程完成后关闭正文编辑器，刷新同一页面，再关闭会话 Tab 后重新打开同一会话
- **THEN** 每次恢复都只加载标记元数据、不提前读取内部上下文正文；初始标记仍在 U1 前，打断标记仍在 U2 前，身份／来源／锚点无重复或漂移；重新右键查看得到同一冻结正文，测试保存各阶段截图、request_id 和实际退出码

### Requirement: 元数据和按需正文读取保持交互预算

系统 SHALL 复用真实 Workbench／Gateway／Backend 验证加载和查看，元数据读取不得遍历全历史、重建全部请求或进行全库完整性审计。既有128 Turn fixture 的后端历史 reader p95 MUST≤200ms、目标100ms，浏览器 prepend／append 和锚点恢复 MUST≤200ms；不超过512KiB的普通正文暖 API p95 MUST≤500ms、max≤1500ms，首次正文在编辑器可见 MUST≤3000ms，并遵守已有更严格预算。测试 SHALL 保留至少20个暖样本及 p50／p95／max、数据规模、request_id、正文读取次数；不可用占位和平均值不能替代正文可见终点。

#### Scenario: 大来源和无关历史不拖慢普通打开
- **WHEN** 同一历史数据包含大段来源正文及大量不属于当前页的历史记录
- **THEN** 默认页面只进行页级元数据查询且正文读取为零，查询计划与实际读取量证明没有全量扫描；普通请求及锚点恢复满足预算，超限大正文单列验证而不污染普通样本
