# session-fifo-message-delivery Specification

## Purpose
为每个会话提供可预测且适合 Web 操作的用户消息投递队列，默认按接受顺序逐条消费，允许用户显式重排尚未领取的普通消息，且普通消息优先于持久任务续跑，并只通过投递策略选择安全边界。消息从队列取出后即视为已发送，不承诺崩溃后的重试或恢复。
## Requirements
### Requirement: Thread 消息按权威调度顺序逐条领取

系统 SHALL 为每条被接受的用户消息创建一个会话队列项，并在精确 Thread 的持久队列中按服务端调度位置消费。入队身份与准入序号不可变；默认按接受顺序，显式重排只修改未领取的普通用户消息的调度位置；队列中只有当前队首可以领取。

#### Scenario: 后来的消息不得绕过队首

- **WHEN** 消息 A 先于消息 B 被同一会话接受，A 仍在等待其投递边界，且用户未显式重排
- **THEN** 系统 MUST 保持 A 在 B 之前，且不得投递、启动或注入 B

#### Scenario: 并发入队仍形成单一顺序

- **WHEN** 同一会话的多个客户端并发提交用户消息
- **THEN** 系统 MUST 在会话级线性化点为每条消息分配唯一入队序号，并在同一持久 owner 中确定默认调度位置；已领取的执行不受后到消息或重排抢占

#### Scenario: 空闲会话提交首条消息

- **WHEN** 会话没有正在执行的 turn，客户端提交一条用户消息
- **THEN** 系统 MUST 先记录队列项，再将该队首消息在空闲安全边界投递，不得绕过队列直接创建无队列来源的执行

### Requirement: 队首消息必须遵循显式投递策略

每个未消费队列项 SHALL 带有且只能带有一个投递策略：`after_turn`、`after_tool_result` 或 `after_interrupt`。策略只决定队首消息最早可以被投递的边界，不得改变消息顺序。

#### Scenario: turn 结束策略

- **WHEN** 队首消息的策略为 `after_turn`，且当前 turn 到达正常结束或已提交的终止边界
- **THEN** 系统 MUST 在该边界之后投递该队首消息，并将其作为一条独立用户消息消费

#### Scenario: tool-result 边界策略

- **WHEN** 队首消息的策略为 `after_tool_result`，且当前执行完成一个完整的 tool-result 边界
- **THEN** 系统 MUST 允许在该边界之后、下一次模型请求之前投递该队首消息；如果当前 turn 在产生 tool-result 之前结束，系统 MUST 使用 turn 结束作为安全回退边界，避免队列永久阻塞

#### Scenario: interrupt 边界策略

- **WHEN** 队首消息的策略为 `after_interrupt`，且当前执行在 interrupt 请求后到达已提交的 interrupt 边界
- **THEN** 系统 MUST 在该边界之后投递该队首消息；单独修改策略不得为尾部消息触发 interrupt，也不得绕过当前队首

### Requirement: 投递不得破坏工具调用边界

系统 MUST 将 assistant 的 tool call 与其对应的 tool result 视为不可拆分的边界单元，不得在二者之间投递任何用户消息。每个投递边界 SHALL 先完成边界事件的持久化，再进行队首消息的消费或注入。

#### Scenario: tool call 尚未返回结果

- **WHEN** 当前执行已经产生 assistant tool call，但对应 tool result 尚未完成
- **THEN** 即使队首策略为 `after_tool_result`，系统也 MUST 保持该消息等待，不得把它插入未完成的 tool call/result 对

#### Scenario: 边界消费与崩溃竞态

- **WHEN** 系统在取出队首消息后、启动或完成后续执行之前发生崩溃
- **THEN** 该消息 MAY 从恢复队列中丢失；系统 MUST NOT 通过 delivery attempt 重试它，也 MUST NOT 影响已经写入的会话历史

### Requirement: 队列消息必须逐条消费且禁止聚合

系统 SHALL 每次只消费一个队列项。任何执行请求、上下文注入、状态转换和实时事件 MUST 能明确关联到单个消息；系统 MUST NOT 将多个队列项拼接为一个 prompt、一个 Job 或一个合并事件。

#### Scenario: 连续消息逐条执行

- **WHEN** 队列依次包含 A、B、C，且 A 到达可投递边界
- **THEN** 系统 MUST 只消费 A，B 和 C 仍保持原顺序等待下一次各自的投递边界

#### Scenario: 不再产生 steering 合并

- **WHEN** 多条消息连续等待同一个当前 turn 结束
- **THEN** 系统 MUST 为每条消息分别产生投递和执行记录，不得产生合并后的内容或将 B、C 标记为附属于 A

### Requirement: 显式重排只改变未领取用户消息的调度位置

系统 SHALL 接受精确 Thread 的完整普通用户消息子序列和 expected_thread_revision，在同一 SQLite 写事务核对版本、成员与领取状态，更新这些消息原有槽位；系统消息和后台任务不得被客户端重新归类或移动。过期版本、缺项、重复项及已领取项 SHALL 返回冲突，且不改变队列。策略变更仍不改变顺序，不触发中断。撤回只取消选定未领取项，保留可读历史。

#### Scenario: B 显式移动到 A 前

- **WHEN** A、B 尚未领取，用户基于当前版本将 B 移到 A 前
- **THEN** 默认先领取 B，实际上下文不包含未执行 A；以后领取 A 时按 B、A 的消费顺序组装上下文，消息／Turn 身份与准入序号不改变

#### Scenario: 重排与领取并发

- **WHEN** 用户拖拽期间另一操作已领取队首或推进 Thread revision
- **THEN** 拒绝过期排列，前端静默重读完整权威快照；不盲恢复拖拽前顺序、不显示重排错误行或 Toast

### Requirement: 普通用户消息优先于持久任务续跑

同一 Thread SHALL 沿既有执行队列先消费全部已接受、未领取的普通用户消息，再领取 Goal、定时／条件任务等续跑执行。已领取执行不抢占；投递策略仍决定队首的合法安全边界。已经接受的任务事实沿原任务生命周期合同处理，暂停影响后续准入，不建立跨库撤销事务。尚未领取任务的提示不得提前进入用户执行的消费选集。

#### Scenario: 任务先排队、用户随后回复

- **WHEN** 一个任务续跑已排队但尚未领取，用户经 Composer 发送普通回复
- **THEN** 用户消息先领取；任务保持原身份等待，不拼接到用户消息上下文

### Requirement: 队列状态必须可持久化并透明恢复

系统 SHALL 持久化仍在等待队列中的消息内容、附件、入队序号和投递策略。只有持久化成功后，接口才能确认该消息已入队；重启后 SHALL 按持久调度位置与优先级恢复仍存在的 queued 消息。已取出的消息不进入恢复状态，持久化或进程崩溃可以使其丢失，但不得删除或伪造旧会话历史。

#### Scenario: 尚未取出的消息在重启后恢复

- **WHEN** 消息 A、B 已收到入队成功响应，随后服务进程崩溃并重启
- **THEN** 系统 MUST 恢复文件中仍存在的 A、B 顺序和策略，并从恢复后的队首继续消费

#### Scenario: 崩溃发生在确认之前

- **WHEN** 服务在入队持久化完成前崩溃
- **THEN** 该次提交可以不出现在恢复队列中，但系统 MUST 不得影响已存在的会话历史，并且客户端不能收到该消息已入队的成功确认

#### Scenario: 取出后的消息允许丢失

- **WHEN** 服务在队首消息已经取出后崩溃
- **THEN** 系统 MAY 丢失这条消息，但 MUST 保留可读的旧历史，且不得创建 delivering 恢复记录

### Requirement: Web 界面必须以按钮表达投递策略

维护的 Web 客户端 SHALL 展示队列的权威顺序、队首标记、每条消息的投递策略和等待原因。每条尚未消费的消息 SHALL 提供用于切换三个投递策略的按钮；按钮必须支持悬停提示，并在可访问的 focus 状态下提供同等说明。界面 SHALL 通过专用拖拽把手及 Alt+上下方向键重排服务端标为 reorderable 的消息，乐观更新并静默同步完整快照；本地未确认提交、系统消息及已领取项不提供把手。重排不改变投递策略，不增加 steering/queued 分组或立即发送按钮。

#### Scenario: 用户查看队列顺序

- **WHEN** 会话中存在多个待处理消息
- **THEN** Web 界面 MUST 按服务端快照显示稳定的队列顺序，并明确标识当前只有队首可以投递

#### Scenario: 用户修改尾部策略

- **WHEN** 用户点击队尾消息的投递策略按钮
- **THEN** 界面 MUST 只提交该消息的策略更新，并在服务端成功响应后用完整权威快照更新队列，不得本地调整消息顺序

#### Scenario: 边界等待状态

- **WHEN** 队首消息尚未到达其策略允许的边界
- **THEN** 界面 MUST 显示对应的等待状态和策略说明，不能把等待中的消息显示为已投递或已执行

#### Scenario: 策略更新失败

- **WHEN** 策略按钮请求被服务端拒绝或网络请求失败
- **THEN** 界面 MUST 显示错误并重新获取队列快照，不得保留未经服务端确认的本地策略或顺序

### Requirement: 队列事件必须能被多个 Web 客户端一致消费

系统 SHALL 在入队、策略更新、撤回和边界到达时发布包含会话标识、消息标识、入队序号、当前策略和队列快照版本的事件或可查询状态；消息取出后使用既有 Job 生命周期事件表示执行。客户端 MUST 以服务端快照为权威，不得通过事件顺序推测或合并不存在的消息。

#### Scenario: 两个 Web 客户端同时观察策略更新

- **WHEN** 客户端 X 修改队列项 B 的策略，客户端 Y 同时订阅该会话事件
- **THEN** X 和 Y 最终 MUST 显示相同的队列顺序、策略和消费状态；任何较旧快照不得覆盖更新后的版本

### Requirement: 未确认消息必须持有不可变且可恢复的输入

客户端 SHALL 在首次网络提交前，按稳定操作身份完整持久化冻结的正文、目标、投递／运行选项及有序附件输入；MUST NOT 仅保存指向可变草稿的键或临时页面URL。复用的附件引用 SHALL 在未确认期间保持可读取，必要字节由原存储保留；冻结失败不得发送。用户继续编辑或清空草稿 MUST NOT 改变冻结请求，原身份重试只使用该输入；修改后明确重提使用新身份。权威接收和稳定身份交接可恢复后 SHALL 释放本操作的冻结输入及独占引用，不能删除其他草稿或业务对象共享的数据。

#### Scenario: 待确认A时草稿改成B或清空
- **WHEN** 消息A已发出但结果未知，用户把Composer改为B或清空，然后刷新页面
- **THEN** 恢复仍能按原操作身份取得并对账A的原正文和附件，B的草稿不被覆盖，不能用B或空正文重试A

#### Scenario: 冻结持久化失败
- **WHEN** 消息输入或必要附件无法完整保存到可恢复存储
- **THEN** 请求尚未发出，界面明确保留输入并报告失败，不显示已可靠提交

#### Scenario: 原操作被明确拒绝后编辑或丢弃
- **WHEN** 权威确认消息A未被接收且终结拒绝，而当前草稿已改为B
- **THEN** A成为可编辑失败项，不再自动发送或按结果未知对账；向草稿或明确重提的新操作完整持久交接输入，或用户明确丢弃后，旧记录及独占附件引用被释放，B及共享附件保持；重启不重新发送被拒绝的A

#### Scenario: 结果未知时用户关闭错误提示
- **WHEN** 消息A可能已被接收但尚无法确认，用户关闭提示或取消本地等待
- **THEN** 保留原操作身份及必要冻结输入，不将本地取消当作服务端撤回，也不删除唯一恢复依据；身份载荷冲突先对账原操作

### Requirement: 消息提交必须从客户端操作交接到唯一权威队列项

用户消息提交 SHALL 按跨端同步合同保留稳定操作身份，权威接收回执关联该操作与唯一的 message、Job、适用的 Turn 和 Thread 身份，并保留原队列顺序依据。重复提交同一操作 MUST 返回同一接收事实而不再次入队；不同载荷复用身份 MUST 冲突。前端本地提交队列只负责未确认提交，收到回执后 SHALL 交接为后端队列／Job 的镜像，不得成为第二个执行调度器。

#### Scenario: 入队成功响应丢失后重试
- **WHEN** 消息已持久入队而客户端因超时使用原操作身份重试
- **THEN** 返回原消息及 Job 身份，队列中仅有一项且入队序号不变，前端不会出现本地待发送与后端排队的重复行

#### Scenario: 两个不同操作提交相同正文
- **WHEN** 用户明确发送两次相同正文且两次操作身份不同
- **THEN** 两条消息分别入队，服务端不得以正文相同误去重，仍保持既有 FIFO 顺序

### Requirement: 队列状态与执行状态必须按权威身份同步

队列镜像 SHALL 使用权威 snapshot_version 或覆盖同一状态的同步版本，取出后的执行 SHALL 关联已有 Job 生命周期。出队／开始执行的权威投影 SHALL 复用原调度边界的 dispatch.queue_snapshot_version 关联队列变化；客户端 SHALL 按owner／Thread保存最高已确认队列水位，空队列仍保留它，低水位快照不得应用。同一Job执行生命周期的已开始／终态 MUST NOT 被queued投影覆盖；缺少关联依据的通知仅触发有界确认，不将Job版本或事件cursor与队列版本比较。前端 MUST 区分等待接收、已入队、等待投递边界、开始执行及执行终态；队列快照中缺少某项本身不能证明该项已成功执行或未被接收。策略修改、撤回和重连 SHALL 通过同一版本与对账规则更新，保持原顺序和投递策略合同；水位随原范围缓存释放，不新增持久队列副本。

#### Scenario: 已接收消息仍等待执行边界
- **WHEN** 后端已确认消息但其策略要求继续等待当前 turn 或工具结果边界
- **THEN** 本地提交等待结束，消息继续以原身份显示为后端排队项及等待原因，不显示为已完成，也不再次提交

#### Scenario: 旧队列快照晚于开始执行事件到达
- **WHEN** 客户端已确认某 Job 开始执行，较旧的 queued 快照随后到达
- **THEN** 界面按已确认dispatch队列水位拒绝旧快照，不把该消息复活为待发送或重新调度，保持已确认的Job执行状态

#### Scenario: 队列清空后旧非空快照迟到
- **WHEN** 客户端已应用版本12的空队列，随后收到版本11的非空快照
- **THEN** 即使当前没有队列元素，仍根据保留的版本12水位拒绝旧快照，不重新显示旧排队项

### Requirement: 提交幂等不得扩大出队后的执行恢复保证

本变更 SHALL 保留默认接受顺序、显式重排及用户优先规则、工具调用安全边界及现有出队后不保证崩溃重试的合同。命令去重用于避免重复接收，MUST NOT 被解释为端到端 exactly-once 执行；消息已取出后即使执行结果缺失，也不得由前端 outbox、Gateway 或新 delivery attempt 自动重新入队。能够确认接收而无法确认执行结果时 SHALL 透明显示该事实。

#### Scenario: 消息出队后进程崩溃
- **WHEN** 服务端已取出消息但在后续执行完成前崩溃，恢复时无法取得完整执行结果
- **THEN** 客户端保留既有可读历史且不自动重发，按可查询事实显示执行状态未知或明确错误，不伪报成功


### Requirement: 主 Agent 可以非阻塞地给用户留言

内置 ask_user_async SHALL 仅接受 Markdown 正文，一次调用持久保存一条留言并立即返回原 question_id 和 saved，不等待答案。仅主 Agent 可用；子 Agent 经父 Agent 转达。留言只负责留存，不暂停任务、不创建审批或等待执行；用户通过原 Composer 发送普通消息回复，不建立答案 API 或自动已回答状态。

Composer 上方 SHALL 提供默认折叠的留言入口，折叠时仅观察数量／revision，展开才有界分页读取正文；复用现有 Markdown 渲染器，文件引用仅在点击后读取正文。列表只提供逐条删除；删除墓碑阻止原工具操作重放复活留言。失效通知沿既有 EventChannel SSE，不轮询、不从 Trace 重建。Tab 的工作区／Session／Thread 归属显式固定，迟到响应不得写到别的 Tab。

#### Scenario: 用户隔日阅读和普通回复

- **WHEN** Agent 留言后正常结束，用户隔日打开会话、展开列表并经 Composer 回复
- **THEN** 留言仍可读，回复进入普通用户队列；留言不自动消失或改变任务状态，用户可逐条删除

#### Scenario: fork 与回退

- **WHEN** 用户 fork 或回退包含提问工具调用的历史
- **THEN** 原工具历史可读；fork 不复制可操作留言或队列，回退及同操作重放不复活已删除留言
