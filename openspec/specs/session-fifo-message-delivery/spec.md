# session-fifo-message-delivery Specification

## Purpose
为每个会话提供可预测且适合 Web 操作的用户消息投递队列，确保消息严格按照入队顺序逐条消费，并只通过投递策略选择安全边界。消息从队列取出后即视为已发送，不承诺崩溃后的重试或恢复。
## Requirements
### Requirement: 会话用户消息必须严格 FIFO

系统 SHALL 为每条被接受的用户消息创建一个会话队列项，并按照服务端为该会话确定的入队序号消费。入队序号一旦分配，不得因为投递策略、当前执行状态或客户端操作而改变；队列中只有队首消息可以进入投递流程。

#### Scenario: 后来的消息不得绕过队首

- **WHEN** 消息 A 先于消息 B 被同一会话接受，A 仍在等待其投递边界
- **THEN** 系统 MUST 保持 A 在 B 之前，且不得投递、启动或注入 B

#### Scenario: 并发入队仍形成单一顺序

- **WHEN** 同一会话的多个客户端并发提交用户消息
- **THEN** 系统 MUST 在会话级线性化点为每条消息分配唯一入队序号，并以该序号作为唯一消费顺序

#### Scenario: 空闲会话提交首条消息

- **WHEN** 会话没有正在执行的 turn，客户端提交一条用户消息
- **THEN** 系统 MUST 先记录队列项，再将该队首消息在空闲安全边界投递，不得绕过队列直接创建无队列来源的执行

### Requirement: 队首消息必须遵循显式投递策略

每个未消费队列项 SHALL 带有且只能带有一个投递策略：`after_turn`、`after_tool_result` 或 `after_interrupt`。策略只决定队首消息最早可以被投递的边界，不得改变消息顺序。

#### Scenario: turn 结束策略

- **WHEN** 队首消息的策略为 `after_turn`，且当前 turn 到达正常结束或已提交的终止边界
- **THEN** 系统 MUST 在该边界之后投递该队首消息，并将其作为一条独立用户消息消费

#### Scenario: tool-result 边界策略

- **WHEN** 队首消息的策略为 `after_tool_result`，且当前执行完成一个完整的 tool-result 边界
- **THEN** 系统 MUST 允许在该边界之后、下一次模型请求之前投递该队首消息；如果当前 turn 在产生 tool-result 之前结束，系统 MUST 使用 turn 结束作为安全回退边界，避免队列永久阻塞

#### Scenario: interrupt 边界策略

- **WHEN** 队首消息的策略为 `after_interrupt`，且当前执行在 interrupt 请求后到达已提交的 interrupt 边界
- **THEN** 系统 MUST 在该边界之后投递该队首消息；单独修改策略不得为尾部消息触发 interrupt，也不得绕过当前队首

### Requirement: 投递不得破坏工具调用边界

系统 MUST 将 assistant 的 tool call 与其对应的 tool result 视为不可拆分的边界单元，不得在二者之间投递任何用户消息。每个投递边界 SHALL 先完成边界事件的持久化，再进行队首消息的消费或注入。

#### Scenario: tool call 尚未返回结果

- **WHEN** 当前执行已经产生 assistant tool call，但对应 tool result 尚未完成
- **THEN** 即使队首策略为 `after_tool_result`，系统也 MUST 保持该消息等待，不得把它插入未完成的 tool call/result 对

#### Scenario: 边界消费与崩溃竞态

- **WHEN** 系统在取出队首消息后、启动或完成后续执行之前发生崩溃
- **THEN** 该消息 MAY 从恢复队列中丢失；系统 MUST NOT 通过 delivery attempt 重试它，也 MUST NOT 影响已经写入的会话历史

### Requirement: 队列消息必须逐条消费且禁止聚合

系统 SHALL 每次只消费一个队列项。任何执行请求、上下文注入、状态转换和实时事件 MUST 能明确关联到单个消息；系统 MUST NOT 将多个队列项拼接为一个 prompt、一个 Job 或一个合并事件。

#### Scenario: 连续消息逐条执行

- **WHEN** 队列依次包含 A、B、C，且 A 到达可投递边界
- **THEN** 系统 MUST 只消费 A，B 和 C 仍保持原顺序等待下一次各自的投递边界

#### Scenario: 不再产生 steering 合并

- **WHEN** 多条消息连续等待同一个当前 turn 结束
- **THEN** 系统 MUST 为每条消息分别产生投递和执行记录，不得产生合并后的内容或将 B、C 标记为附属于 A

### Requirement: 队列控制操作不得改变顺序

对尚未消费的队列项，系统 SHALL 允许修改该项的正文、附件或投递策略（若产品继续提供这些编辑能力），但任何修改 MUST 保持其入队序号和与其他消息的相对顺序。系统 MUST 不再提供按任意消息重排、提升到队首或立即发送的语义。

#### Scenario: 尾部消息修改投递策略

- **WHEN** B 位于 A 之后，客户端把 B 的策略从 `after_turn` 修改为 `after_interrupt`
- **THEN** B 的策略 MUST 更新成功，但 A 仍是队首，B 不得因此提前投递，A/B 的入队序号不得改变

#### Scenario: 非法重排或提升

- **WHEN** 客户端请求拖拽重排、提升某条消息或立即发送非队首消息
- **THEN** 系统 MUST 拒绝该请求并返回明确错误，且拒绝操作不得改变队列快照

#### Scenario: 队列项撤回

- **WHEN** 客户端撤回尚未消费的队列项
- **THEN** 系统 MUST 只移除该项并保留其余消息的相对顺序，下一条原有消息才可以成为队首

### Requirement: 队列状态必须可持久化并透明恢复

系统 SHALL 持久化仍在等待队列中的消息内容、附件、入队序号和投递策略。只有持久化成功后，接口才能确认该消息已入队；重启后 MAY 按入队序号恢复文件中仍存在的 queued 消息。已取出的消息不进入恢复状态，持久化或进程崩溃可以使其丢失，但不得删除或伪造旧会话历史。

#### Scenario: 尚未取出的消息在重启后恢复

- **WHEN** 消息 A、B 已收到入队成功响应，随后服务进程崩溃并重启
- **THEN** 系统 MUST 恢复文件中仍存在的 A、B 顺序和策略，并从恢复后的队首继续消费

#### Scenario: 崩溃发生在确认之前

- **WHEN** 服务在入队持久化完成前崩溃
- **THEN** 该次提交可以不出现在恢复队列中，但系统 MUST 不得影响已存在的会话历史，并且客户端不能收到该消息已入队的成功确认

#### Scenario: 取出后的消息允许丢失

- **WHEN** 服务在队首消息已经取出后崩溃
- **THEN** 系统 MAY 丢失这条消息，但 MUST 保留可读的旧历史，且不得创建 delivering 恢复记录

### Requirement: Web 界面必须以按钮表达投递策略

维护的 Web 客户端 SHALL 展示队列的只读顺序、队首标记、每条消息的投递策略和等待原因。每条尚未消费的消息 SHALL 提供用于切换三个投递策略的按钮；按钮必须支持悬停提示，并在可访问的 focus 状态下提供同等说明。界面 MUST 不提供拖拽排序、优先级提升、steering/queued 分组或立即发送按钮。

#### Scenario: 用户查看队列顺序

- **WHEN** 会话中存在多个待处理消息
- **THEN** Web 界面 MUST 按服务端快照显示稳定的队列顺序，并明确标识当前只有队首可以投递

#### Scenario: 用户修改尾部策略

- **WHEN** 用户点击队尾消息的投递策略按钮
- **THEN** 界面 MUST 只提交该消息的策略更新，并在服务端成功响应后用完整权威快照更新队列，不得本地调整消息顺序

#### Scenario: 边界等待状态

- **WHEN** 队首消息尚未到达其策略允许的边界
- **THEN** 界面 MUST 显示对应的等待状态和策略说明，不能把等待中的消息显示为已投递或已执行

#### Scenario: 策略更新失败

- **WHEN** 策略按钮请求被服务端拒绝或网络请求失败
- **THEN** 界面 MUST 显示错误并重新获取队列快照，不得保留未经服务端确认的本地策略或顺序

### Requirement: 队列事件必须能被多个 Web 客户端一致消费

系统 SHALL 在入队、策略更新、撤回和边界到达时发布包含会话标识、消息标识、入队序号、当前策略和队列快照版本的事件或可查询状态；消息取出后使用既有 Job 生命周期事件表示执行。客户端 MUST 以服务端快照为权威，不得通过事件顺序推测或合并不存在的消息。

#### Scenario: 两个 Web 客户端同时观察策略更新

- **WHEN** 客户端 X 修改队列项 B 的策略，客户端 Y 同时订阅该会话事件
- **THEN** X 和 Y 最终 MUST 显示相同的队列顺序、策略和消费状态；任何较旧快照不得覆盖更新后的版本
