# VRN 目录导航、分段解析与跨 Gateway 文件操作：OpenSpec 修改建议

## 交接状态与功能目标

- 记录时间：2026-10-05 16:46（UTC+8）。这是一版可继续修改的侧会话交接草案，不是已冻结的业务契约；主线程参考并审定后，把决定写入正式 OpenSpec 的唯一 owner。
- 本次只整理交接内容，没有修改 OpenSpec 或实现这些功能，也没有验证跨端工具链。以下现状基于本次静态核查；主线程继续前应复核当前提交与在途改动。
- 用户希望模型拿到目录根 VRN 后，可以追加文件或子目录路径，并通过 `ls/read/grep/apply_patch` 等工具操作目标端。目标端也运行 BoxTeam Gateway，工具体验应接近操作本地工作区，搜索与补丁在目标端执行。
- 用户提出部分资源允许模型推导子路径，另一些资源只能按 owner 提供的引用和领域规则访问。这里需要定义资源导航语义，不以建立完整的进程沙箱为前置条件。

## 1. 当前设计与实现的限制

1. 统一寻址 OpenSpec 已有 `ResourceIdentity / VRN / real path` 三层职责分离；scope 闭集为 `workspace / user / gateway / inline`，各 scope 都要求显式 scope_id。尚未定义完整的“目录、文件、领域对象”导航与文件操作合同。
2. `app/services/infrastructure/resource_platform/virtual_resources/grammar.py` 的 skills 尾段固定为 `{skill_name}/SKILL.md`；目录根及 `references/rules.md` 等附属文件无法表达。`SKILL.md` 是固定文件名的特例，不表示一般文件名允许点号。
3. grammar 已按 kind 分支，但仍整体拒绝非 ASCII 与百分号编码，多个动态段共用 `[A-Za-z0-9_-]`。这套逻辑身份字符规则不足以表达普通文件名。
4. `virtual_resources/resolver.py` 按完整 VRN 精确匹配 catalog；仅放宽 grammar，仍不能解析未逐一登记的目录子文件。`values.py` 的资源操作集合目前为 `read_content / activate / observe`，尚不是文件操作接口。
5. 文件工具另走 `app/agents/workspace_tool_paths.py` 的工作区路径合同，其中还存在独立的 `boxteam-session://` 映射；`apply_patch` 按工作区根解析路径。改造前须检索全部调用方，决定如何统一接入 VRN owner，避免留下并行寻址链路。
6. OpenSpec 已规定可选 gateway authority 与有界星型解析，但本次核查的主树 parser 仍把首段当 scope，未接入 authority。规范 task 3.4 也标为待实施；该状态不能当作跨端操作已完成的证据。

## 2. 保留归属层级，让技能包根成为目录资源

gateway authority、scope、scope_id、`resources` 固定段与 kind 全部保留。目录导航只扩展 kind 后面的资源语义，不取消 scope，也不让子路径改变资源归属。

以下是建议形态，不是当前已实现接口：

```text
技能包根：
boxteam://gw-b/workspace/ws-1/resources/skills/review

包内文件：
boxteam://gw-b/workspace/ws-1/resources/skills/review/SKILL.md
boxteam://gw-b/workspace/ws-1/resources/skills/review/references/rules.md
boxteam://gw-b/workspace/ws-1/resources/skills/review/scripts/check.py
```

其中 `gw-b` 是 gateway authority，`workspace` 是 scope，`ws-1` 是 scope_id，`review` 是技能包名。其它 scope 仍使用各自既有的 scope_id 规则。`SKILL.md` 保留为入口文件，技能包根本身允许列目录。

建议由 owner 登记目录根，统一解析器区分“根资源＋相对路径”，然后由所属文件系统定位子节点；无需把目录里的每个临时文件都登记到语义资源 catalog。子文件 VRN 仍是地址，不能直接充当 ResourceIdentity。

工作区源码文件树也需要可导航根：当前四个 kind 没有通用源码文件树的明确合同。技能目录能力不能替代整个工作区的文件访问。是否新增文件树 kind、根形态如何命名，应由统一寻址 owner 正式登记；此草案不把任何候选 kind 当作已定稿值。

## 3. 分结构、分类型解析，而不是全 URI 共用文件名白名单

建议保持一个解析入口，按以下顺序完成校验，再访问底层资源：

1. 解析公共结构：scheme、可选 gateway authority、scope、scope_id、固定 `resources` 与 kind；各字段分别按其规范校验。
2. 由已登记 kind 选择尾部语法。skills 先识别技能包根；领域对象则按自己的身份和结构解析。
3. 对允许目录导航的根，剩余部分按相对文件路径解析；对象与单文件资源不自动获得目录语义。
4. 校验导航能力、操作能力和目标归属后，由目标 owner 执行操作。

身份段可以继续采用受限字符集。目录尾部应支持正常文件名中的点号、中文、空格等，并单独规定 URI 编码、规范形式和解码顺序。原有“整体拒绝 `%` / 非 ASCII”的规则需要按区段修订，不能只增加某几个扩展名特例。

编码只能由唯一 owner 处理。分隔符、`.` / `..`、空段、字面百分号及编码后的分隔符应有明确规则，保证 `%2F` / `%252F` 不被不同调用方重复解码成不同层级。需要根范围检查的目录操作统一完成检查；这只是文件工具的定位边界，不代表终端具有操作系统沙箱。

现有 authority 可省略的形态是自定义段序：`boxteam://workspace/...` 经通用 URL parser 解析时，authority 会是 `workspace`。主线程须明确这种省略如何无歧义解析，不能让调用方各自把 URL netloc 直接当 gateway_id。

## 4. 区分可导航目录、单文件与领域对象

| 资源形态 | 建议的模型操作合同 |
| --- | --- |
| 技能包、正式定义的工作区文件树 | 发布可导航根；允许追加相对路径、列目录、搜索，按 owner 允许的能力读取或修改 |
| 单文件资源 | 直接访问该文件；不能继续追加路径，把文件当目录 |
| Session、assembly、配置来源等领域对象 | 用 owner 提供的引用、结构化 view 与领域 API 访问；不推断其底层 SQLite、检查点或私有目录可被文件工具编辑 |

导航能力与操作能力分开表达。可列目录、可读取不等于可写；URI 用于定位，目标 owner 依据已有请求身份和资源能力决定能执行哪些操作。展示元数据可包含节点类型、导航方式和允许的操作，具体字段名由主线程在统一合同中定稿。

“允许推导”指根或 URI 模板公布了有效的子路径规则，并允许模型指定新建文件的路径；不代表猜对任何 URI 就获得权限。“不承诺推导”的资源应提供发现与引用方式，不能仅凭它的 URI 外观推断存在文件树。

## 5. 跨端工具就地执行，Gateway 保持路由职责

```text
模型工具：目标 VRN ＋ 操作参数
  → 本地 Gateway 解析并路由目标
  → 目标 Gateway 透明转发
  → 目标工作区后端的资源 owner 定位并执行
  → 返回 VRN／相对路径、内容、搜索匹配或补丁结果
```

- Gateway 只负责目标路由与代理，不承担 Agent 业务逻辑，也不直接读写工作区业务数据。资源真实路径只在所属 owner 的底层调用中使用。
- `ls/read/grep` 是理解 VRN 的工具接口；原生 shell 命令不会自动识别 `boxteam://`。grep 在目标端搜索后返回匹配结果。
- `apply_patch` 的补丁在目标端校验并应用，沿用目标端的错误、冲突和落盘证据合同。建议一次补丁明确绑定一个目标工作区／资源根，所有文件路径都按该根解析。
- 不可达、未登记、不支持操作或能力不足都应显式失败；不得静默改成本地同名工作区操作。跨界响应保持逻辑地址与内容，不外露 real path 或 credential。
- 工作中的可变目录与固定修订快照需要分别明确读写合同。现有 `revision / view / cursor` 并列字段继续保留；固定修订内容不能被文件写操作悄悄改写。
- 如果后续要求同样透明地运行终端、测试或构建，还需明确进程执行目标；目录导航本身不包含远端进程执行能力。本次先交接目录与文件工具需求。

## 6. 主线程需要修改的 OpenSpec 范围与顺序

1. **统一 owner**：优先修订 `openspec/changes/add-unified-virtual-resource-addressing/` 的 proposal、design、specs 与 tasks，加入目录根、子路径、导航／操作能力、分段字符规则及工作区文件树的正式寻址决定。同步修订现有 task 1.4、3.4、7.1 和星型解析任务，移除与新合同矛盾的整体字符限制；实际任务编号以当前文件为准。
2. **调用方引用**：检查 `migrate-session-context-uri-to-vrn`、`add-context-injection-lifecycle`、`add-multi-workspace-backend-mounting`、`add-workspace-persistent-resource-management` 的相关约束，只引用统一 owner。保留 ResourceIdentity、scope_id、结构化 view/revision/cursor 与 real path 隔离，不把目录语义扩散到所有对象。
3. **文件工具消费合同**：将现有文件路径解析、目录访问、搜索和补丁链路的接入任务明确列出。若需要独立工具变更，其语法、导航能力和拒绝码仍引用统一 owner；不要建立第二套 VRN parser。新增拒绝码由统一 owner 集中登记。
4. **实施顺序**：先审定公共合同，再完成一条本地技能目录纵向链路，接入同一套远端路由并验证目标端执行，随后覆盖工作区文件树。删除旧寻址实现与平移全部消费方必须一起交付。
5. **验证与状态**：更新所有受影响的 OpenSpec artifacts，运行相应严格校验；任务完成勾选依据实际实现与验收证据，不能把本交接或已写好的规范当作功能完成。

建议补充的验收场景（本次均未执行）：

- 同一技能包的根、入口文件与多层子文件可寻址；目录列举返回可继续使用的子地址，未登记的真实子文件可访问，新文件可在允许写入的根下创建。
- 点号、中文、空格、百分号及多层路径按单一规范往返；逻辑身份段仍遵守自己的规则，路径解释不因调用方不同而改变。
- 本地与远端工具拥有一致的输入输出合同；远端 grep 与补丁实际发生在目标端，相同相对路径不会串 Gateway 或工作区，也不依赖当前激活工作区。
- 只读根拒绝写入，领域对象拒绝不支持的目录操作；未知地址、失效资源、远端故障与修订冲突返回 owner 登记的明确错误。
- 目录定位不越出所属根；跨界结果、模型载荷与持久引用不含真实路径；固定修订读取与可变目录编辑的行为明确。
- 源码调用方、测试与协议类型同步迁移，旧 URI／旧解析实现物理下线。测试运行遵守仓库进程外保护及产物目录规范。

## 7. 可导航目录的工具覆盖建议（待审定）

除 `ls/read_file/grep/apply_patch` 外，建议审查以下能力。工具名表示候选入口或既有入口，不代表新增功能已获审定或已实现；不是每项能力都必须单独增加模型工具。

| 能力／工具 | 建议优先级 | 用途与覆盖边界 |
| --- | --- | --- |
| `glob` | 首批接入 | 按文件名模式找文件，如 `**/*.py`；仓库已有实现，根路径需统一支持 VRN，pattern 与根地址分开传递 |
| `stat/info` | 首批覆盖 | 查询节点类型、大小、修改时间、可操作能力及可用的 revision；可通过 `ls` 的详细结果或单节点查询覆盖，无需强制增加独立入口 |
| `write_file / edit_file` | 既有入口同步接入 | 仓库已有创建文本文件及精确替换实现。与 `apply_patch` 共享寻址、目标归属和写入 owner，明确创建／覆盖／替换合同；不各自维护解析与跨端执行链 |
| `mkdir` | 目录管理切片 | 创建空目录；同时明确写文件时创建父目录的规则，仅有文本补丁不足以表达空目录 |
| `move/rename` | 目录管理切片 | 移动目录、二进制文件及一般节点；文本文件的补丁移动不能代替通用文件系统移动。首批明确同一目标内的移动合同 |
| `copy` | 目录管理切片 | 复制目录树或二进制文件；跨 Gateway 复制涉及两个目标及内容传输，需另外审定范围 |
| `remove` | 目录管理切片 | 删除目录或二进制文件；普通文本文件删除可以继续走补丁。非空目录是否递归删除必须由请求明确表达 |
| 二进制／媒体读取与写入 | 按实际素材需求 | 覆盖图片、附件、压缩包等，明确内容类型与附件／内容句柄的传输方式。图片读取按模型支持的内容形式返回，不能只作为文本读取 |
| `exec_command` 及终端生命周期工具 | 完整开发体验的配套切片 | 在目标端以 VRN 指定的工作目录执行脚本、测试和构建；已有 `write_stdin`、终端列表与终止工具也要保持同一目标归属。文件操作能力不自动包含命令执行能力 |
| `diff/status` | 复查时覆盖 | 查看更改与 Git 状态；优先经明确执行目标的命令工具运行目标端 Git，通常不必新增独立工具。无 Git 的目录需另定比较方式 |
| `watch/tail` | 后续可选 | 监听文件变化、跟随追加日志；只有需要持续观察时再明确订阅与生命周期合同 |

首批重点是目录发现和元数据，以及已有文件读写工具的统一 VRN 接入。目录管理、二进制内容与进程执行按实际切片推进。目录管理可以合并为一个带 operation 的入口；元数据可以合入已有目录工具；Git 审查可以复用命令工具，避免仅为了 API 齐全而堆积模型工具。

既有工具核查入口：`app/agents/workspace_filesystem_tools.py` 声明并接入 `ls/read_file/write_file/edit_file/glob/grep`；`app/agents/tools/terminal.py` 定义终端命令与生命周期工具。它们具有本地实现，不表示已支持 VRN 或跨 Gateway。

技能加载需要单独保持领域语义：目录工具读取 `SKILL.md` 不应隐式激活技能；`skill_load` 的激活、上下文注入与来源追踪继续由其 owner 负责。当前提示词还要求技能正文通过 `skill_load` 获取，主线程须在调整目录读取合同时同步审定这项行为，不能只改路径解析器。

## 8. 下一轮可继续完善的决定

- 工作区文件树的正式 kind、根地址，以及技能包根是否统一使用无尾斜杠的规范形式。
- 分段编码和文件名规则，特别是字面 `%`、Unicode 与跨平台文件名的规范表达。
- 导航能力和操作能力的最小字段、拒绝码，以及根与子文件的 ResourceIdentity／revision 合同。
- 文件工具接收完整子 VRN，还是接收“根 VRN＋相对路径”，或将二者统一归一到同一个内部请求；不能维护两套语义。
- 工具清单的首批范围，以及已有 `write_file/edit_file` 与 `apply_patch` 的共用写入合同；目录读取技能入口与 `skill_load` 激活的行为边界。
- 现有 `boxteam-session://` 与工作区文件工具的替换范围，以及后续终端／测试跨端执行是否纳入另一个明确切片。

这些项目用于后续审查与补充，不在本交接中虚构最终决定。
